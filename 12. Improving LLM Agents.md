## Chapter 12. Improving LLM Agents

We have built evaluators, set up CI to catch regressions, and deployed monitoring to track production quality. We have also surfaced failure modes through error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) and data analysis ([Chapter 11](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch11.html#sec_data_analysis)). Now we use all of that to make the agent better.

In this chapter, you will learn:

- How to improve accuracy through prompt refinement, structural changes, and heavier interventions like fine-tuning
- How to reduce cost through model selection, token reduction, caching, and model cascades
- How to verify that each change actually helps using the evaluators and CI infrastructure from earlier chapters

Both accuracy and cost improvements depend on reliable measurement. Without evaluators ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)) and monitoring ([Chapter 9](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch09.html#sec_ci_cd)), we cannot tell whether a change helps or hurts.

## Accuracy Optimization

When an agent fails evaluations or frustrates users, accuracy is usually the first thing to fix. We can organize the techniques by effort level: low, medium, and high.

## Low Effort: Prompt Refinement

The fastest way to improve accuracy is to refine the prompt. Prompt refinement includes clarifying instructions, adding few-shot examples, and steering the model with explicit personas. These are low-effort changes that can have a big impact.

*Fix specification errors first.* As discussed in [“Defining the Right Metrics (What to Measure)”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_what_to_measure), many failures come from the Gulf of Specification: the prompt does not clearly say what we want, so the model makes a reasonable guess that happens to be wrong. These are the cheapest failures to fix because they only require editing the prompt, not improving the model’s ability to generalize.

For our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), suppose a user asks “Find me homes near downtown.” The model returns a mix of houses, condos, and townhomes. The user only wanted single-family houses. This is a specification error: our prompt says `Search for listings matching the user's preferences` but never defines what “homes” means. The fix is to add a clarification: `When the user says "homes," default to single-family houses unless they specify otherwise (e.g., "condos," "townhomes").`

We want to fix specification errors *before* building evaluators, because there is no point measuring whether the model generalizes on a task we have not clearly defined yet.

###### Tip

Before writing any evaluator, skim your 10 worst traces and ask: “Did the prompt actually say what I wanted?” In our experience, half of early failures are specification errors that disappear with a one-line prompt edit, saving weeks of evaluator development on a problem that was never a model limitation.

*Add a few examples.* We can include two or three representative input/output pairs directly in the prompt. These examples should target failure cases we have observed during error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), but they should be distinct from the test cases used in CI. Reusing CI test cases as few-shot examples inflates our evaluation scores without actually improving the agent’s behavior on new inputs.

If we have a library of many good examples, we can go further and select them dynamically. Instead of always including the same fixed examples, we can retrieve the most similar ones to the current query (using embedding similarity) and include those as few-shot examples. This gives the model more relevant guidance per query without bloating every prompt with every example we have.

*Use role-based guidance.* Giving the model a persona (for example, “You are a careful tax advisor”) can help guide tone and reasoning style, especially for open-ended tasks.

*Ask for step-by-step reasoning.* For tasks involving logic or multiple steps, explicitly asking the model to “think step by step” can improve correctness and completeness. This technique is sometimes called chain-of-thought prompting.

These changes are fast to try and easy to validate with the golden test sets from our CI setup ([Chapter 9](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch09.html#sec_ci_cd)).

## Medium Effort: Changing How the Agent Works

When prompt edits are not enough, we can change how the agent is put together.

*Break the task into smaller steps.* Instead of a single LLM call that does everything, we can decompose the task into a sequence of focused steps. For example, imagine we are building a research agent that looks for relevant information in a corpus of external data and synthesizes it into a report. Instead of one call to an LLM to produce the full report from a query, we could break the task down:

1. Extract the user’s preferences or constraints.
2. Query a database or search tool.
3. Filter or summarize the results.
4. Generate a final answer or message.

Each step is easier to evaluate independently. If the generated report contains errors, we can trace the failure to a specific step (for example, bad retrieval or incorrect filtering) rather than debugging a single monolithic call.

*Tune RAG retrieval.* In many agents, retrieval quality drives overall performance more than generation quality does. We can improve retrieval by reworking the query sent to the retriever, adjusting how source documents are chunked, tuning the number of chunks retrieved, and adding a lightweight reranking step before passing results to the LLM. [Chapter 7](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch07.html#sec_rag_evaluation) covers how to measure retrieval quality in detail.

[DoorDash reported](https://careersatdoordash.com/blog/doordash-simulation-evaluation-flywheel-to-develop-llm-chatbots-at-scale/) a concrete case of this in 2026. Their customer support chatbot was hallucinating answers to questions from dashers (the drivers who deliver orders), for instance inventing refund policies or misinterpreting details about an order. The engineers found that the chatbot was seeing too much raw information at once: every event in a delivery’s history (pickup time, location pings, chat messages, status changes) was being dumped into the prompt, and the model was getting confused by the volume. Their fix was to add a layer that summarized the relevant delivery history into a clean, structured form before passing it to the chatbot. No model change, no retraining, just a better way of organizing what the model already had access to. They tested the change by running thousands of simulated conversations against the chatbot (each simulated conversation was generated by another LLM playing the role of a dasher) and measured hallucination rates in the results. The fix cut hallucinations by roughly 90% in those simulations, and the improvement held up in production.

*Fix tool descriptions.* If the model repeatedly calls a tool incorrectly (wrong argument formats, missing parameters), we can revisit how we describe the tool in the prompt (see the tool calling evaluation stages in [Chapter 8](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch08.html#sec_agentic_systems)). For our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), suppose the `check_calendar` tool expects dates in `YYYY-MM-DD` format, but the model keeps passing strings like `"next Saturday"` or `"March 10th"`. The tool description says `date: string` but does not specify the format. Changing it to `date: string in YYYY-MM-DD format (e.g., "2025-03-10")` fixes the argument generation error for every query that involves scheduling.

*Sample multiple responses and pick the best.* For tasks that involve reasoning or judgment, we can run the same prompt multiple times (with temperature > 0) and compare the outputs. If most responses agree on an answer, that answer is more likely to be correct. This is called *self-consistency*. For example, if we ask our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)) to classify a user’s intent, we can sample three responses. If two out of three say “scheduling request” and one says “listing question,” we go with “scheduling request.” Self-consistency costs more per query (we pay for multiple LLM calls), so it is best reserved for high-stakes decisions where getting it right matters more than speed.

*Add a verification step.* We can add a second LLM call that checks the first one’s output. For example, after the agent drafts an email, a separate call can verify: “Does this email accurately reflect the listing data? Does it match the client’s persona?” This catches errors that the first call missed. The tradeoff is latency and cost (two calls instead of one), so we typically use verification on the most important outputs, not on every request.

*Add guardrails.* We can add synchronous checks that run before the output reaches the user (see the guardrails discussion in [Chapter 9](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch09.html#sec_ci_cd)). For example, a regex can catch generated emails that contain patterns resembling social security numbers. A SQL parser can reject syntactically invalid queries before they hit the database. These are cheap and fast, and they prevent the most embarrassing failures even when the model occasionally slips.

## High Effort: Model-Level Changes

If prompt and architecture changes have not solved the problem, we can consider model-level interventions. These take more effort and typically require high-quality labeled data.

*Fine-tuning.* Fine-tuning means taking a pre-trained model and continuing to train it on our own set of example inputs and outputs, so that the model learns to handle our specific task in a specific way. When we have hundreds of high-quality labeled examples and cannot fix the issue with prompting alone, fine-tuning is an option. It is slower and more expensive to set up than prompt changes, but it can lock in improvements for well-defined, high-value tasks where nothing else works.

*Human review loops.* For tasks with high stakes or hard-to-detect failure modes, we can build a lightweight interface ([Chapter 10](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch10.html#sec_interfaces)) for human reviewers to check and annotate a small sample of outputs regularly. Annotations can feed back into fine-tuning datasets and can also reveal failure modes that automated evaluators miss.

*Prompt optimization.* For agents where prompts are reused across thousands of requests, even small wording changes can have a large aggregate impact. We can treat the prompt as a tunable artifact: try variations, test them against held-out golden sets, and keep what improves accuracy. Some teams formalize this process using grid search over template variations or automated optimization frameworks.[^1]

## Cost Optimization

Once accuracy meets requirements, we can start reducing cost. The approach is the same as with accuracy: find the biggest cost drivers, make targeted changes, and verify with evaluators that quality stays intact.

## Match Model Size to Task Complexity

Not every step in an agent needs the most powerful (and most expensive) LLM. We can map each task to the smallest model that meets its accuracy requirements.

Lightweight models work well for simple, high-volume tasks: sentiment classification, extracting fields from structured text, or recognizing basic user intent. We can reserve the largest models for sub-tasks that require advanced reasoning, follow complex instructions, or where accuracy stakes are high.

For example, in our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), a small model could classify incoming messages into categories like “listing question,” “scheduling request,” or “general inquiry.” Only complex queries, like those requiring a customized explanation of how a property compares to recent sales, would be routed to a more capable model.

## Cut Token Usage

Since most LLM providers charge based on the number of tokens processed (both input and output), reducing token count directly reduces cost.

*Trim input tokens.* Make sure instructions are concise. For RAG-based agents, tune the number of documents retrieved and placed in the prompt. If the agent makes multiple LLM calls that analyze the same long document, consider adding an initial step where a cheaper model summarizes the document first. Subsequent calls then operate on the shorter summary, which reduces input tokens for each downstream call. For instance, when analyzing a lengthy legal contract to extract various clauses and obligations, summarizing the contract once upfront can be much cheaper than feeding the full text to multiple specialized extraction prompts.

*Trim output tokens.* Explicitly instruct the LLM to be concise when appropriate. For tasks where the output follows a known structure, requesting output in a compact format like YAML (rather than natural language prose or JSON, which includes many braces and brackets) can reduce the number of generated tokens.

## Make Prompts Cache-Friendly

Many teams overlook caching as a cost reduction technique. Many LLM API providers (including OpenAI, Google, and Anthropic) use caching mechanisms that reduce both latency and cost for repeated requests. When [Anthropic introduced prompt caching for Claude in 2024](https://www.anthropic.com/news/prompt-caching), they reported that cache hits cost 10% of the base input token price (a 90% reduction) and that latency on long prompts dropped by up to 85%. These numbers only apply when the *prefix* of the prompt matches byte-for-byte across requests, which is why the way we structure our prompts matters.

Modern LLMs are based on the Transformer architecture. At each step, a Transformer computes a set of “key” and “value” vectors for every token processed so far. Keys serve as lookup signals to decide which past tokens matter most. Values carry the actual information those tokens contribute. When generating long sequences or handling many similar prompts, recomputing all key-value states from scratch is expensive.

LLM inference engines mitigate this redundant computation by storing intermediate key-value (KV) states in a cache. When a new prompt begins with the exact same token sequence (the *prefix*), the engine reuses the cached KV states for that prefix and computes only the states for the new suffix. This reuse reduces both latency and compute cost.

Caching applies only when the prefix matches exactly. A single-token change invalidates the cache from that point forward and forces full recomputation. Consider a simple task: “Think of a friendlier way to say: X,” where X is any piece of text. If we place the instruction *before* the varying data, then every request shares the same long prefix (the instruction), and the provider can cache and reuse it. If instead the instruction comes *after* the data, only the first few tokens of the data (which may happen to overlap between requests) remain in the shared prefix, so there is minimal cache reuse.

[Figure 12-1](#fig-kv-cache-prefix) illustrates this. Request 1 computes everything from scratch. Request 2 starts with the same system instruction, so the provider can reuse the cached KV states from Request 1 and only compute the new user query. Request 3 puts the user query first, which changes the prefix, so there is no cache hit and everything is recomputed.

![kv cache prefix](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/kv-cache-prefix.svg)

kv cache prefix

To take advantage of caching:

- Put constant instructions before any user-provided or changing data.
- Keep formatting and phrasing consistent across requests.
- Consult your LLM provider’s documentation for the associated cost savings, as pricing for cached vs. non-cached tokens varies between providers.

###### Note

Even whitespace differences break the cache prefix. If your prompt templates insert variable-length content (e.g., a user name) before the main instructions, every request computes from scratch. Move all static instructions to the top and all variable data to the bottom.

## Batching

If some of our LLM calls are not time-sensitive, we can batch them. Instead of sending one request at a time, we group multiple requests into a single API call and process them together. This reduces per-request overhead. Some providers offer explicit discounts for batched workloads. For example, OpenAI’s Batch API processes requests within a 24-hour window at half the cost of synchronous calls.

Batching works well for offline tasks: running evaluators on a day’s worth of production traces, generating summaries for a backlog of documents, or scoring a dataset for CI. It does not work for real-time user-facing requests where latency matters.

## Distillation

If we have a large model that performs well on a task but costs too much to run at scale, we can try *distillation*. The idea is to use the large model (the “teacher”) to generate labeled outputs on a set of examples, then fine-tune a smaller model (the “student”) on those outputs. The student learns to mimic the teacher’s behavior at a fraction of the inference cost.

Distillation is different from standard fine-tuning. In standard fine-tuning, we train on human-labeled data. In distillation, we train on the teacher model’s outputs. This means we can generate training data cheaply by running the teacher on unlabeled inputs, which makes it easier to scale up the training set.

The catch is that the student will not exceed the teacher’s quality. If the teacher hallucinates on certain inputs, the student will learn those same mistakes. We evaluate the distilled model with the same rigor we apply to any other change (golden dataset checks, online monitoring), and we compare its error profile to the teacher’s to make sure it has not picked up new failure modes.

## Model Cascades

Suppose we are running an LLM-as-Judge evaluator in production and it costs $0.02 per trace. On 10,000 traces a day, that is $200/day. We want to keep the same accuracy but spend less.

A *model cascade* does this by setting a *target accuracy*: the minimum agreement rate between the cascade’s output and the expensive model’s output (for example, 95% agreement). We then route each query through a cheap model first. If the cheap model is confident in its answer, we accept it. If it is not confident, we escalate to the expensive model. The goal is to meet the target accuracy while sending as few queries as possible to the expensive model.

We call the expensive model the *oracle* (the best system we currently have) and the cheap model the *proxy*. [Figure 12-2](#fig-model-cascade) shows the flow.

![model cascade](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/model-cascade.svg)

model cascade

The oracle does not need to be perfect. It is simply our best current system. The cascade tries to reproduce the oracle’s answers at closer to the proxy’s cost.

*Estimating confidence.* The cascade depends on knowing how confident the proxy is in each answer. To understand how we can get this, recall that an LLM generates text one *token* at a time (a token is roughly a word or part of a word, as we discussed in [Chapter 1](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch01.html#sec_intro)). At each step, the model assigns a probability to every token in its vocabulary. The token with the highest probability is the one it outputs. So when the model generates `true`, it has internally computed a probability for `true` and a probability for every other token (`false`, `maybe`, `yes`, etc.). If the probability of `true` is 0.90 and the probability of `false` is 0.10, the model is very confident. If `true` is 0.55 and `false` is 0.45, it is close to a coin flip.

This is why *classification tasks* (where the answer is a single token like `true` or `false`) are the easiest case for cascades. We can look at the probabilities of the valid answers and directly measure how sure the model is.

*Approach 1: Logprobs for classification tasks.* Most LLM APIs do not return probabilities directly. They return *log probabilities* (logprobs), which are the natural logarithm of the probabilities.[^2] A probability of 0.90 becomes a logprob of about -0.10. A probability of 0.01 becomes a logprob of about -4.60. Logprobs are always negative or zero, and closer to zero means higher probability.

When we request logprobs from the API, most providers return the logprobs for the top 5 to 20 most likely tokens. For a prompt that ends with “Answer true or false,” both `true` and `false` almost always appear in that top list. We convert both logprobs back to probabilities with `exp()`, normalize so they sum to 1, and use the higher one as the confidence score. [Figure 12-3](#fig-logprob-confidence) walks through an example where the model is about 90% confident in `true`.

![logprob confidence](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/logprob-confidence.svg)

logprob confidence

For open-ended tasks where the answer is a full sentence or paragraph, this approach does not work. The answer is many tokens long, and the top-token logprobs only tell us about one token at a time. There is no way to compare “the probability of this full answer” against “the probability of a different full answer” because the API does not give us that.

*Approach 2: Verbalized confidence for open-ended tasks.* For these tasks, we can ask the model to state its own confidence. For example, we can append to the prompt: “On a scale from 0 to 10, how confident are you in your answer?” The model produces a number, and we use that as the confidence score. This is a cruder estimate than logprobs. Some models are overconfident. Others are underconfident. We check whether the verbalized confidence actually predicts correctness during the threshold-tuning step described below (where we run the proxy and oracle on a held-out set and see how well the proxy’s confidence correlates with matching the oracle). If verbalized confidence does not correlate, we cannot use it for the cascade.

There is a second complication with open-ended tasks. When we tune the cascade threshold (described below), we compare the proxy’s answer to the oracle’s answer on a held-out set to decide whether they agree. For classification, this is straightforward: if the proxy says `true` and the oracle says `true`, they agree. For open-ended tasks, two answers can convey the same information using completely different words. We typically use an LLM-as-Judge ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)) to score whether the proxy’s output conveys the same content as the oracle’s. This adds cost to the threshold-tuning step (we run a judge on every example in the held-out set), but it only happens offline, once, not on every production query.

###### Note

If the proxy’s confidence scores (whether from logprobs or verbalized) do not correlate with whether its answers match the oracle, we will not find a threshold that meets the target accuracy. The cascade then defaults to sending everything to the oracle. We have not saved any money, but nothing has broken. Better-calibrated proxies save more because we can trust them on a larger fraction of queries.

*Tuning the cascade threshold.* Before deploying the cascade, we calibrate it offline to find the confidence threshold.

We take a held-out evaluation set of *N* examples and run both the proxy and the oracle on all of them. For each example, we record the proxy’s answer, its confidence score, and the oracle’s answer (which we treat as ground truth). We then find the lowest confidence threshold where the proxy’s answers agree with the oracle at least as often as our target accuracy requires (for example, 95% of the time). [“Offline Calibration for a Model Cascade”](#tab_cascade_algorithm) shows the procedure.

At runtime, every production query goes to the proxy first. If the proxy’s confidence is at or above *t*, we return the proxy’s answer. If it is below *t*, we escalate to the oracle.

One consequence of this two-step routing is that escalated queries are slower than if we had called the oracle directly, because they pass through both the proxy and the oracle. This is acceptable when most queries (70-80%) are handled by the proxy alone, since the average latency across all queries still drops.

If we have more than two models at different cost levels, we can chain them: try the cheapest model first, escalate to the next one if confidence is low, and so on until one is confident enough or we reach the oracle. Each model gets its own threshold, calibrated the same way.

For more on model cascades, see the FrugalGPT paper (\[Link to Come\], Chen et al. 2023), which introduced LLM cascades and showed they can match GPT-4 quality at a fraction of the cost. Task cascades (\[Link to Come\], Shankar et al. 2026) extend this idea by varying what the model is asked to do at each stage, not just which model is used. For example, a cheap model might answer a simplified version of the question, and only queries it cannot handle get passed to a more expensive model with the full, detailed prompt.

## Closing: The Lifecycle Continues

This book followed the *Analyze, Measure, Improve* lifecycle introduced in [Chapter 1](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch01.html#sec_intro). We started by reading traces and identifying failure modes ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)). We built evaluators that quantify those failures at scale ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)). We integrated those evaluators into CI so that regressions are caught before they reach users ([Chapter 9](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch09.html#sec_ci_cd)). In this chapter, we used the evidence from those earlier phases to make concrete improvements in both accuracy and cost.

Every improvement can change the failure distribution. A prompt change that fixes one class of errors may introduce another. A cost optimization that routes queries to a cheaper model may degrade accuracy in subtle ways. The response is to keep the loop running: analyze the new behavior, measure the impact, and improve again.

Evaluation datasets go stale as products evolve and user behavior shifts. Error taxonomies need periodic revisiting. New evaluators appear when new failure modes surface. Improvements go through CI so they persist across model updates and code changes.

Even an informal version of this loop (review some traces each week, update the golden set, fix the worst prompt) compounds over time.
