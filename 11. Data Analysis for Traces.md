## Chapter 11. Data Analysis for Traces

The last chapter was about how we might use custom interfaces to accelerate our error analysis. This chapter is going to be about applying a broader *data analysis* mindset to reviewing traces. Error analysis tells us *why* something might look bad, and is actually a type of data analysis. We will cover other techniques you can use to spot patterns across many traces at once, and decide which ones to read closely.

In this chapter, you will learn:

- How to use exploratory data analysis (EDA) and clustering to surface hypotheses about your traces for further investigation
- How to compute and plot descriptive statistics over traces (turns, latency, tool calls, tokens, sentiment) and use them to spot patterns
- How to use semantic search to find more traces that look like a problem you have already spotted
- How to use AI coding assistants (Claude Code, Codex) to accelerate this work without letting them confabulate your analysis for you

## EDA and Clustering to Surface Hypotheses

Exploratory Data Analysis (EDA) is the practice of poking at a dataset to generate hypotheses about it. John Tukey introduced the term in the 1970s as a counterweight to *confirmatory* analysis, which is the familiar routine of fitting a model and running a significance test. Before we can confirm anything, we need to know what to confirm, and EDA is how we get there. We plot, group, filter, and read until we have a hypothesis sharp enough to test.

For LLM traces, EDA is how we move from “something is off” to “here is a specific failure mode.” Error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) is itself a form of EDA: reading traces and grouping them into a taxonomy is the same loop applied to text. This section covers techniques that extend that practice beyond trace-by-trace reading.

A huge mistake people make with EDA is treating a cluster as a failure mode. Clusters do not map cleanly to failure modes. The same goes for correlations, bar charts, and other EDA outputs. We treat them as prompts to go read the underlying traces. We start with a rough hypothesis, pick a slice of the data, read the traces in that slice, and either sharpen the hypothesis or drop it. We expect to drop most of our first tries.

## Clustering

We introduced clustering in [Chapter 10](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch10.html#sec_interfaces) as a way to surface patterns across groups of traces. Here we use it for hypothesis generation: we read a few representatives from each cluster and ask what their differences suggest about where the agent is going wrong.

Sometimes we cluster and find nothing useful. We cannot tell the clusters apart, or we just see categories we already knew about (queries about condos, queries about houses). That is information too. Either our embedding is not capturing the variation we care about, or the variation we care about is not the dominant axis in the data. For our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), we clustered on query embeddings and got the obvious groups (scheduling, search, email generation) but nothing about where the agent was failing. When we clustered the *final email* instead, we found a small group of messages that all opened with a long apology before getting to any listings. That was a tone problem we had missed in our earlier error analysis.

## Beyond Clustering

Clustering is one tool in the EDA toolkit. Beyond clustering, we look at per-trace metrics (number of turns, latency, tool calls, input and output tokens, sentiment, user segment, time of day) and ask how they are distributed, how they correlate, and how they break down by metadata. Here are a few data analysis techniques we have found useful:

Plot the distribution of a metric.\* With a histogram or box plot of turns-per-session, latency, or tokens, we can see whether the metric is roughly unimodal, bimodal (two humps instead of one, often because we have two distinct groups of users or two failure modes mixed together), or long-tailed (a few traces much bigger than the rest). If we see a bimodal shape, we split the dataset and read each mode separately.

Cross-tabulate metadata against outcomes

If we log a thumbs-up/down signal, we can break it down by client persona, agent version, time of day, or session length. For example, we might chart thumbs-down rate by session length. If long sessions fail more often, we dig into that as our next hypothesis.

Look for correlations between metrics

We can plot tool calls against latency, or tool calls against thumbs-down rate, to see whether the two are related. If they are (e.g. traces with more tool calls also get more thumbs-down), we dig into that relationship.

Filter to a subset and read

Pick an interesting slice (thumbs-down traces, traces over five turns, traces with a specific tool call) and read 20 of them back-to-back. Reading in a concentrated batch is how we catch patterns we would miss reading one trace at a time.

Hunt for outliers

An outlier is a trace whose value on some metric (latency, tokens, number of tool calls) is much larger or smaller than typical. We use two common rules for flagging them:

- Interquartile range (IQR): let Q1 and Q3 be the 25th and 75th percentiles of the metric and IQR = Q3 - Q1. Flag any trace below Q1 - 1.5 \* IQR or above Q3 + 1.5 \* IQR. This rule is robust to skew, which trace metrics usually have (a few very slow or very chatty sessions pull the mean, but not the quartiles).
- Percentile cut: flag the top 1% and bottom 1%. This rule is simpler, and we end up with a fixed number of traces to read.

## Semantic Search to Find Related Traces

One question we find ourselves repeatedly asking is: once we spot a failure mode, how do we find more traces like it? Error analysis often surfaces only one or two bad examples, but what we want is the full population (how common is this, and does it hit one user segment more than others?). Semantic search is our usual answer.

We introduced embedding-based search in [Chapter 10](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch10.html#sec_interfaces). Here we use it to expand a known failure mode into a larger set. Two query patterns we rely on:

Seed with a problematic trace

Pick a trace that exhibits the failure (say, the apologetic email from the clustering example) and search for its nearest neighbors by embedding. We get back a ranked list of candidates and read them.

Query with a natural-language description

Write out what we are looking for (“email that starts with an apology before listing any homes”) and embed that string. This is useful when we have a description of the pattern but not a canonical example.

Semantic search has one big caveat: embedding similarity is not the same as our notion of similarity. Two traces can be near each other in embedding space because they share topic words (both mention “tour scheduling”), even when the failure we care about is narrower (the agent double-booked a showing in both).

One workaround we have found useful is to ask an LLM agent to extract application-specific features from each trace (e.g., did the agent book a tour? did it mention a conflicting time? did it hedge?) and embed those features, or a short summary, instead of the raw trace. The agent itself can propose the features if we give it a handful of examples of the failure mode. With feature embeddings, we get closer to our notion of similarity.

## Using AI Coding Assistants

The work in this chapter (loading traces, plotting distributions, clustering, running semantic search) is mostly code we would rather not write from scratch. AI coding assistants like Claude Code, Codex, and notebook-embedded agents accelerate the mechanics considerably. Here is how we use them without letting them take over the analysis.

Our typical setup is to drop a file of traces (JSON or JSONL), a short description of the application and what each field means, and, where relevant, the application code itself into a working directory, and then open a Claude Code or Codex session pointed at that directory. Once the assistant has all of that in context, we find ourselves asking for the kinds of things we would otherwise script ourselves. That might be plots of distributions (a histogram of turns-per-session with a log y-axis, then split by user segment), a classifier rubric or regex drafted from a handful of examples of a failure mode, a summary of a cluster of traces we paste in, or a direct search of the traces for a pattern we describe (“find traces where the agent apologized before giving any listings”). We use the session as our scratchpad for most of the work in this chapter.

Early in EDA especially, we find it useful to ask for many charts in one go and then read only the ones that look interesting. Most will be uninformative and that is expected. For example, we might ask for thumbs-down rate broken down by session length, user segment, agent version, time of day, and tool-call count all at once, and then only read traces behind the one breakdown where something looks off.

Then, once we are looking for a specific pattern, asking the assistant to search the traces directly is a lightweight alternative to the semantic search from the previous section. For a few thousand short traces, it lets us skip the embedding-index setup entirely. At larger scale (tens of thousands of traces, or longer traces each) direct search breaks down. The assistant cannot fit the full dataset in context, and we have to fall back to embedding search or a proper index.

One pitfall to avoid is asking the assistant directly why the traces are failing. It might make something up from whatever examples it has seen, and the answer will sound reasonable even when it is wrong. So we should stick to asking the assistant to find, summarize, search, or plot. These are activities to aid in our analysis, not do our analysis.

## Putting It Together

Error analysis gives us a taxonomy of failure modes from reading traces closely. Data analysis adds aggregate techniques for seeing those failures across the full trace set at once. We use EDA and clustering to surface hypotheses about failure modes, per-trace metrics (distributions, correlations, outliers) to spot patterns we would miss reading one trace at a time, and semantic search to expand a known failure mode into the full population it affects. AI coding assistants like Claude Code and Codex accelerate the mechanics of all of this (e.g., loading traces, plotting distributions, drafting rubrics, searching for patterns), but we treat their outputs as hypotheses to check against the underlying traces, not as the analysis itself.

In the next chapter, we turn to the improvement work itself: the prompt, code, and model changes that fix the failures we have surfaced, along with the cost-side optimizations that keep production sustainable.
