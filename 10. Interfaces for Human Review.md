## Chapter 10. Interfaces for Human Review

Automated evaluators ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)) handle most of the monitoring, but humans still review a sample of traces regularly to catch issues the evaluators miss and to keep evaluators calibrated as the team’s understanding of quality evolves (the criteria drift we discussed in [Chapter 4](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch04.html#sec_collaborative_evaluation)). The question is how to do that review efficiently. LLM traces are complex. A single trace can include the user query along with multiple tool calls with structured arguments, retrieved documents, intermediate reasoning, and the final output. Reviewing these in a spreadsheet is painful, so we have found it very useful to build our own review interfaces. Not only is it easier to get through more traces, we end up actually *wanting* to look at more of our data, for as long as we are able to keep discovering new failure modes.

In this chapter, you will learn:

- Why custom review interfaces work better than spreadsheets and generic tools
- Key interface principles from Human-Computer Interaction (HCI) that apply to reviewing LLM agent outputs
- Features that make reviewing faster and more reliable, organized by category
- Strategies for selecting the most informative traces to review
- How to embed review into your team’s engineering workflow

## The Case for Custom Review Interfaces

When teams first start reviewing LLM outputs, they usually start with a spreadsheet. This is natural: most logging systems can export traces as CSV, and spreadsheets are familiar to everyone on the team. The problem is that LLM traces do not fit well into rows and columns.

Consider what a single trace from our real estate assistant looks like in a spreadsheet row. The user asked: “Find 3-bedroom homes under $600k near downtown and email the top two to my client.” The agent made three tool calls (a listing search, a filter, and a calendar check), retrieved six listing documents, produced intermediate reasoning about which listings best match, and generated a two-paragraph email. In a spreadsheet, all of that lands in a single row. The email text overflows its cell. The tool calls appear as a JSON blob in one column. The retrieved listings sit in another JSON blob next door. To judge whether the agent picked the right listings, you have to parse the JSON by eye, cross-reference it with the query constraints, and then read the email to check if it accurately reflects the results. That is three separate acts of mental reconstruction for one trace.

In a custom interface, we can lay out that same trace so it reads naturally. The user query goes at the top. Each tool call gets a collapsible panel with arguments and return values formatted clearly. The generated email looks like an actual email, with the client name, subject line, and body. A sidebar shows the client persona and retrieved listings. A trace that took five minutes in a spreadsheet takes 30 seconds here.

We can build these tools with frameworks like Streamlit or Gradio. LLMs can also help generate basic interfaces through rapid prototyping. For example, asking an LLM coding assistant to “generate an HTML dashboard served via FastAPI to review text generation outputs with pass/fail buttons and a feedback textbox” can produce a functional starting point in minutes.

If you already use an observability platform (such as Langsmith, Braintrust, or Arize) that lets you browse traces, start there. Use it for a week and write down every moment where you feel friction: a missing filter, an unreadable JSON blob, a slow page load. Those friction points tell you what to build first.

Once you have a sense of what the default tools get wrong, the next question is what a good review interface looks like. Jakob Nielsen’s usability heuristics give us a practical starting framework. [Table 10-1](#tab_hci_principles) maps the most relevant principles to concrete design choices for LLM agent review tools.

| Principle | Design implication |
| --- | --- |
| Visibility of system status | Show which trace is being reviewed, how many remain, and feedback status. Provide timely progress indicators. |
| Match between system and real world | Use familiar terms from rubrics and evaluation criteria. Make mappings intuitive. |
| User control and freedom | Allow navigation (next/previous), undo, and defer actions. Prevent lock-in of any notes. |
| Consistency and standards | Reuse layouts, terminology, and behaviors across traces. |
| Error prevention | Use distinct labeling controls. Enforce requirements like rationale for “Fail” to reduce mistakes. |
| Recognition rather than recall | Show predefined failure modes and explanations visually to reduce cognitive load. |
| Flexibility and efficiency of use | Offer shortcuts and accelerators for expert users. Keep the interface intuitive for novices. |
| Aesthetic and minimalist design | Emphasize signal over noise. Highlight inputs and outputs clearly. |

Here is how these principles translate into design choices.

## Essential Interface Elements

A review interface can show the full LLM trace (input, output, and intermediate steps like tool calls, retrievals, and internal reasoning) while keeping things manageable. One way to do this is to collapse less important sections by default and let reviewers expand them with a click when they need more detail.

For feedback collection, we can tag known failure modes using binary checkboxes or buttons based on issues identified during error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) or collaborative evaluation ([Chapter 4](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch04.html#sec_collaborative_evaluation)). Quick overall ratings (thumbs up/down or numeric scores) speed up the process. Open-ended feedback fields let reviewers explain their reasoning, which helps surface unexpected problems and refine evaluation criteria over time.

## Features That Improve Review Speed and Quality

The following enhancements fall into three categories. Some make individual reviews faster, others collect higher-quality feedback, and the rest help reviewers navigate the dataset.

Faster individual reviews:

Keyboard shortcuts

Provide hotkeys for submitting feedback, tagging failure modes, and moving between traces. A reviewer who can press N for Next, F for Fail, and T for “Tone Mismatch” moves through traces two to three times faster than one who clicks buttons.

Visual hierarchy

Emphasize the most important trace components (such as the final output) using layout, color, or segmentation. In our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), highlighting price and location mentions in generated emails makes factual errors jump out immediately.

Progressive disclosure

Show only basic options (“Pass,” “Fail,” “Defer”) at first. Show detailed failure tagging only when the reviewer marks a trace as failed.

###### Tip

Keyboard shortcuts are the single highest-leverage feature for review speed. Even a minimal set (Next, Pass, Fail, Defer) can double throughput. Add them before investing in any other interface enhancement.

Higher-quality feedback:

Inline annotation

Allow span-level feedback, such as highlighting a problematic sentence or marking a faulty dialogue turn, so reviewers can point to exactly what went wrong.

Feedback templates

Offer frequently used comments (such as “Tone too casual” or “Missing key fact”) as quick-select options, optionally adapted to the selected failure tag.

Defer option

Provide a clear, prominent “Defer” button for uncertain cases. This preserves label accuracy and prevents low-confidence guesses from polluting the dataset.

Better navigation and context:

Contextual metadata

Show relevant metadata (user segment, agent version, automated evaluation results) directly in the interface so reviewers can spot version-specific regressions.

Filters

Allow filtering on dimensions relevant to the product. If users interact with your agent through text, a dedicated app, and a website, you want channel as a filter.

Batch review and bulk actions

Let reviewers examine trace clusters (for example, from the same client persona) and apply the same failure label to multiple examples. This speeds up handling of repetitive issues but should be used carefully.

Progress indicators

Show counts of traces reviewed, grouped by key dimensions, so reviewers can track their progress and know when they are done.

## Case Study: EvalGen

To see these principles in action, consider EvalGen, which applies many of them in a minimal design. *EvalGen* is a lightweight interface for human evaluation of LLM outputs that demonstrates several of these ideas in practice (\[Link to Come\], Shankar et al. 2024). A publicly available version (EvalGen v2) is integrated into ChainForge (\[Link to Come\], Arawjo et al. 2024).

EvalGen displays one output at a time, allows binary feedback (thumbs up/down), supports open-ended comments, and lets reviewers edit past labels. It also includes a rubric builder that automatically extracts candidate evaluation criteria from the original prompt and lets users select which ones to apply during review.

![screenshotevalgenv2](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/screenshotevalgenv2.png)

screenshotevalgenv2

EvalGen prioritizes *which* traces to show based on LLM judge disagreement: when multiple automated evaluators (such as separate LLMs or prompt variants) disagree on a verdict, the system surfaces that example for human review. This is a form of *uncertainty sampling*, which we discuss further in [“Selecting Traces for Human Review”](#sec_sampling_strategies).

EvalGen’s user studies surfaced something deeper: even human reviewers experience *criteria drift*. Over time, annotators refined what “correctness” or “polish” meant, revised prior judgments, and added new failure categories that nobody anticipated up front. This means a review interface can support evaluation as an evolving process, not a static labeling task. We can support going back and revising earlier labels, adding new failure categories mid-stream, and updating rubrics as understanding deepens.

###### Warning

If your review interface does not let reviewers revise earlier labels, criteria drift will silently corrupt your dataset. Reviewers refine their understanding of “correct” as they see more examples, and the labels from the first 20 traces may no longer match the labels from the last 20.

This connects directly to the collaborative evaluation practices discussed in [Chapter 4](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch04.html#sec_collaborative_evaluation), where teams work to align on what quality means. A review interface can make that alignment process easier to do regularly.

## Selecting Traces for Human Review

Even with a well-designed interface, reviewing every production trace is impossible. LLM agents can produce thousands or millions of outputs, and only a fraction can get human review. The question is which traces to show.

## Random Sampling

The simplest approach is to randomly sample traces from the production stream. Random sampling is unbiased and gives a general picture of system performance when the sample size is large enough. However, it misses rare failure modes. If most outputs are already good, reviewers spend their time confirming quality rather than finding problems.

## Uncertainty Sampling

Uncertainty sampling focuses review on traces where automated evaluators disagree or appear unsure. The idea comes from a machine learning technique called *active learning*. In active learning, instead of asking a human to label a random batch of data, the model first identifies the examples it is least sure about and asks the human to label only those, so human effort goes where it is most needed. Uncertainty sampling for trace review works the same way: we show reviewers the traces where the automated evaluators are split or unconfident, on the assumption that these are the most informative to look at by hand.

We can identify uncertainty in several ways:

- A trace fails some evaluation criteria but passes others, suggesting borderline quality.
- An LLM judge produces inconsistent results when run multiple times with temperature greater than zero.
- Different evaluators (for example, a code-based check versus an LLM judge) give conflicting judgments.

This last case is what EvalGen adopted: it surfaced traces for human review specifically when automated judges disagreed.

## Failure-Driven Sampling

Failure-driven sampling pulls traces that some automated signal has already flagged as likely problems. For our real estate assistant, one such signal is a guardrail catching an unsolicited financial recommendation in a generated email; another is a user clicking thumbs-down. Any trace carrying a failure marker goes into the review queue.

Pulling those traces is the fastest way to understand *why* the system fails on cases we already know are bad. A trace shows the whole arc of what happened, which usually points to where in the pipeline things went wrong.

This approach catches most of the obvious problems, but it only catches what our existing signals are already configured to look for. A subtle failure mode that slips past every guardrail—say, the model confusing a neighborhood’s school district—will never show up here, no matter how many traces we review. In machine learning terms, precision is high but recall is low. That is why we cannot rely on failure-driven sampling alone: to catch these unknown unknowns, we also need to review traces the system rates as fine.

In practice, we can blend all three. We can use random sampling as a baseline, uncertainty sampling to catch the ambiguous cases, and failure-driven sampling to handle the obvious problems.

###### Note

A practical split is 50% failure-driven, 30% uncertainty-sampled, and 20% random. The random portion is easy to skip but provides the only unbiased estimate of overall system quality. Without it, review sessions overrepresent edge cases and give a misleadingly pessimistic picture.

## Navigating Trace Groups and Discovering Patterns

Reviewing individual traces catches specific errors, but many issues only become visible when we step back and look at groups of examples. Good review interfaces include tools for exploring patterns across similar traces, especially through clustering and search (see [Chapter 11](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch11.html#sec_data_analysis) for more).

## Clustering

Clustering groups traces that share common features. We can cluster on simple metadata or on semantic similarity.

For our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), we might cluster traces by client persona (“investor,” “first-time buyer”) or by feature used (email generation versus property search). Suppose we pull up the “investor” cluster and review five traces. Four out of five emails open with “Dear \[name\], I hope this message finds you well” and spend two paragraphs on pleasantries before mentioning any properties. We have found a systematic tone problem: the agent writes casual, relationship-building emails when investor clients expect concise, data-driven summaries. Without clustering, these five traces would be scattered among thousands, and the pattern would be invisible.

We can also cluster semantically. Instead of using metadata, we can embed the inputs (such as user queries) or outputs (such as generated emails) and group them based on vector similarity using algorithms like k-means. For example, semantic clustering might uncover a latent category: all queries about “affordable condos near good schools.” Reviewing that cluster shows that the agent consistently ignores HOA fees and misunderstands school-quality indicators, quoting distance to the nearest school instead of actual ratings. This is a systematic factual gap that we can fix with a focused prompt change or tool addition.

Interfaces can surface these clusters visually so reviewers quickly find common patterns, investigate root causes, and prioritize fixes.

## Search and Similarity Tools

Clustering helps with broad exploration. But sometimes, after spotting one problematic trace, we want to find more like it. Review tools should support searching by keyword, metadata, or semantic content.

We can search by keyword to locate traces with specific terms, filter on metadata (`agent_version`, `user_segment`, failure tags) to slice the data precisely, or use semantic search to find conceptually similar traces even when wording varies. For example, if one email from our real estate assistant gives unsolicited financial advice, semantic search can surface other emails with the same problem, even if they use different phrasing.

Together, clustering and search let reviewers move past one-off examples and uncover systematic failures.

## Integrating Human Review into Engineering Workflows

A review interface only matters if people use it regularly and if the feedback actually leads to changes in the system. We make human review part of the team’s normal engineering workflow. If nobody is using the interface, we probably have not reduced the friction enough.

To support regular use, we set up automated systems that surface the right traces at the right time. For example, we might run a daily or weekly job that selects a batch of traces using the sampling strategies from [“Selecting Traces for Human Review”](#sec_sampling_strategies) and notifies reviewers via Slack or email when the batch is ready. For high-priority issues (safety violations, broken tool calls, major regressions), we trigger alerts immediately and route them to on-call reviewers.

Review feedback can flow back into the agent in two ways.

Golden datasets

Traces labeled by reviewers (especially failed ones) go into the CI test set for regression testing. This connects human review to the automated evaluation infrastructure discussed in [Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators).

LLM-as-Judge calibration

Human labels let us monitor whether automated judges are still accurate. If humans repeatedly flag outputs as incorrect that the judge rated as “Pass,” we revise the judge’s prompt, retrain the model, or swap it out entirely ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)).

To keep this loop tight, we can add simple actions to the interface. A reviewer can click a button to add a trace directly to the CI golden set, or file a bug report with trace details already prefilled. A dashboard can show which failure types appear most often and where reviewers disagree with LLM judges, so the team can prioritize fixes.

## Example Walkthrough: Reviewing Real Estate Assistant Emails

To make these ideas concrete, we walk through how a review interface might evolve for our real estate assistant that drafts client emails ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)). Each stage shows how interface choices affect usability, speed, and the quality of feedback.

## Starting with a Spreadsheet

The most basic interface is a spreadsheet. We export logs (the user’s query, client persona, and the generated email) into Google Sheets.

Here is what a single row looks like. Column A holds the trace ID: `tr-8a3f`. Column B has the timestamp. Column C contains the user query, but it is truncated to “Find me 3-bedroom homes under $600k near downto…” Column D has the client persona: “first-time buyer, young couple, budget-conscious.” Column E holds the generated email, but the cell shows only the first line: “Dear Sarah and James, I hope this email finds you well. I wanted to…” To read the rest, we double-click and get a wall of unformatted text with no line breaks. Column F is the “Notes” column, where three different reviewers have typed comments separated by semicolons: “ok; seems long; tone issue maybe?”

After ten traces, we realize we cannot tell whether the listed properties actually match the budget constraint because the tool call results are in Column G as a raw JSON string: `[{"address": "123 Main St", "price": 580000, ...}, {"address": ...}]`. We copy-paste it into a JSON formatter in a separate browser tab to read it.

This is slow, unstructured, and error-prone.

A clear step up is building a lightweight custom UI using Streamlit, Gradio, or an AI coding assistant. The UI shows one trace at a time with the user input, persona context, and generated email clearly separated. Reviewers click Pass/Fail buttons and leave optional comments. ## An Advanced Review Interface

A basic UI still misses features that matter. It does not show intermediate steps like tool calls or external context retrieved during RAG steps. There are no structured failure tags (the axial codes from [Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), no way to highlight specific problems in the output, and no support for reviewing related traces together.

The advanced interface brings all of this together. Individual traces appear with rich, readable layouts that show the input query, persona context, and the full output alongside any intermediate reasoning or tool usage. Emails render with clear visual formatting, highlighting key entities like price, location, or timing so errors stand out immediately.

Reviewers select predefined failure tags (like “Tone Mismatch” or “Hallucinated Feature”), write free-form notes (the open codes from [Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), and use hotkeys to speed up review (N for Next, D to Defer, T for Tone). Contextual metadata (trace ID, agent version, timestamp) appears directly in the interface to help with triage.

The interface also supports group-level exploration. Clustering groups similar emails, such as those for “investor clients” or “affordable condo searches.” Reviewers examine a few examples from each cluster to spot patterns and apply bulk labels to speed things up. Search tools find similar examples (for instance, “all emails that sound too apologetic”) across the dataset.

With the right interface, reviewing LLM agent outputs becomes faster, more consistent, and more useful. The highest-leverage features in practice are hotkeys for faster navigation, structured failure tagging to reduce ambiguity, and clustering to surface repeated failure modes. These produce immediate gains in review speed and label quality with minimal implementation effort.

## Case Study: DocWrangler for Prompt Refinement

Review interfaces can also influence how we improve our systems, not only how we evaluate them. *DocWrangler* is a purpose-built IDE for LLM-powered document processing (\[Link to Come\], Shankar et al. 2025). It demonstrates many of the interface principles from this chapter, particularly how layout, interaction design, and lightweight feedback mechanisms accelerate iterative development.

In DocWrangler, users author prompts to extract, reason about, and make sense of information from unstructured documents. The interface runs a prompt over a batch of documents, then lets users review the outputs one by one. Each screen shows the original document, the generated output, and the prompt that produced it, organized side by side to reduce friction when inspecting failures or inconsistencies.

![dw feedback](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/dw_feedback.png)

dw feedback

The interface encourages *open coding* (writing freeform notes about observed problems, as discussed in [Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)). Users quickly leave natural-language comments on any example, jotting down observations like “missed the date field,” “output order is inconsistent,” or “ignored second table.” These lightweight notes are faster than formal labeling but still capture valuable signals. Over time, they help users notice recurring problems and refine their mental model of what is going wrong.

Once enough notes accumulate, users invoke the *prompt improvement* feature. This takes the current prompt and the accumulated reviewer comments and suggests an updated prompt aimed at fixing the issues. The interface presents both versions side by side for quick inspection.

![dw improvement](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/dw_improvement.png)

While [DocWrangler](https://docetl.org/playground) is tailored to document extraction, the same ideas apply broadly. Interfaces that streamline review and feed findings back into the system accelerate LLM agent development.

## Putting It Together

Automated evaluation scales oversight, but humans remain essential for catching subtle errors and refining what “quality” means. Custom review interfaces, designed with HCI principles, make human review faster and more consistent than spreadsheets or generic tools. Sampling strategies (random, uncertainty-based, failure-driven) focus limited reviewer attention on the most informative traces. Review only matters if it leads to action. Interfaces should make it easy to file bugs, update evaluation datasets, and trigger prompt improvements.

In the next chapter, we zoom out from individual traces and look at how to analyze them in aggregate to find patterns that trace-by-trace review cannot surface.
