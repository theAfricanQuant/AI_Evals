## Chapter 7. Evaluating Retrieval-Augmented Generation

The previous chapters covered evaluation techniques that apply broadly across LLM applications. Now we turn to a specific architecture that introduces its own evaluation challenges: retrieval-augmented generation (RAG).

In this chapter, you will learn:

- How to build evaluation datasets for retrieval using synthetic query generation
- How to measure retrieval quality with Precision@k, Recall@k, MRR, and NDCG@k
- How to tune chunking strategies with grid search
- How to evaluate generation quality using faithfulness and relevance

RAG architectures are pervasive across customer support, enterprise search, scientific QA, and coding assistance. Evaluating RAG requires more than measuring final answer correctness. Each stage of the pipeline (query construction, retrieval, reranking, and generation) can independently introduce failure modes.[^1] For example, failures across these stages are interdependent. If retrieval returns the wrong documents, the generator has no way to produce a correct answer. If the user’s query is ambiguous, retrieval may pull back something only loosely related, and reranking and generation will be working from a bad starting point.

In this chapter, we focus on two parts of the evaluation loop: *analyze* and *measure*. We show how to:

- Analyze whether failures arise in retrieval, in generation, or in the interaction between them.
- Measure retrieval quality using metrics like Recall@k, MRR, and NDCG@k.
- Evaluate generation using context-sensitive metrics such as faithfulness and relevance.

We begin by constructing evaluation datasets for retrieval, then introduce diagnostic metrics and methods for attributing failures across the pipeline.

## Overview

A basic RAG pipeline retrieves context from a knowledge base (e.g., a document corpus, structured table, or the web) based on a query, and feeds it into an LLM for generation. Unlike traditional search, the consumer of this context is the LLM itself, which can process many passages simultaneously. This shifts the retrieval objective: high *recall* becomes critical to ensure we include all potentially relevant content.

However, simply retrieving as many documents as possible is not ideal. LLMs have limited context windows, and irrelevant text can degrade performance. LLM APIs also charge per token, so excess tokens increase cost. To balance coverage and quality, most modern RAG systems use a two-stage retrieval approach.

![=](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/rag-retrieval-workflow.svg)

Stage 1: First-pass retrieval

The first stage scans the entire corpus and returns a broad set of candidates. Here, we can use fast, lightweight methods that are cheap to run over millions of documents. Common choices are embedding-based search with approximate nearest neighbor indexes (for example, FAISS, HNSW, or hosted vector stores like Pinecone or Weaviate on top of embeddings from models like OpenAI’s `text-embedding-3` or Cohere’s `embed-v3`), or sparse retrieval methods like BM25 over an inverted index. The goal at this stage is high *recall*, even at the cost of precision: we want to make sure the right document is somewhere in the candidate set, even if it is not yet at the top.

Stage 2: Reranking

The second stage takes the broad set of candidates from stage 1 and re-orders them more carefully, putting the most relevant ones at the top. A reranker is, intuitively, a more careful “reader.” Where stage 1 compared a single embedding of the query against a single embedding of each document, a reranker looks at the query and a candidate document together and produces a relevance score that takes both into account. Because it considers the pair jointly, it can catch nuances that a one-shot embedding similarity would miss, but it is also more expensive per call, which is why we only run it on the small candidate set instead of the whole corpus. The two common implementations of a reranker are cross-encoder models (such as Cohere Rerank, BGE reranker, or a fine-tuned MiniLM cross-encoder), which are trained specifically to score (query, document) pairs, and LLM-as-reranker setups, where we prompt a general LLM with the retrieved documents and ask it to return a new ordering or per-document scores. At this stage we prioritize precision and ranking quality rather than coverage.

We start by evaluating the retrieval component on its own

Before we assess the quality of generated answers, we verify that the system consistently finds the right context. If the retriever is not surfacing the relevant documents, no amount of prompt engineering or model tuning on the generation side will fix the output.

## Synthetically Generating Query-Answer Pairs

To evaluate retrieval, we need a dataset of queries paired with the specific document *chunks* that contain the correct answers. The most reliable option is to manually curate a set of realistic questions and map each to the exact chunk(s) in which the answer appears. While this provides high-quality supervision, it is often expensive and time-consuming.

To scale up this dataset more easily, we can generate synthetic question-answer-context triples using an LLM ([Figure 7-2](#fig-synthetic-qa-pipeline)).

![synthetic qa pipeline](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/synthetic-qa-pipeline.svg)

synthetic qa pipeline

We start by dividing the documents into chunks, which serve as retrieval “targets.” For each chunk, we prompt the LLM to identify a salient fact and then generate a question that can only be answered using that fact:

```
You are a helpful assistant generating synthetic QA pairs for retrieval
evaluation.

Given a chunk of text, extract a specific, self-contained fact from it.
Then write a question that is directly and unambiguously answered by that
fact alone. Return your output in the following JSON format:

{
  "fact": "...",
  "question": "..."
}

Chunk:
"{text_chunk}"
```

## Creating Harder Synthetic Queries

The basic synthetic generation approach from above tends to produce questions that are easy for a retriever to answer, because each question is built from a single chunk and uses that chunk’s exact wording. A retriever that matches on keywords will find the right chunk most of the time. In production, user queries are messier. They use different phrasing, reference topics that appear in multiple documents, and sometimes ask for comparisons across chunks. To stress-test the retriever, we can generate synthetic questions that deliberately resemble content in multiple chunks but are only correctly answered by one of them:

Select a target chunk

Choose a chunk A from the corpus that contains a clear, fact-based answer.

Identify similar chunks

Use an embedding model or keyword search to find chunks B, C, etc. that are similar to A but do *not* contain the answer.

Generate a discriminative question

Ask the LLM to write a question that is *only* answered by Chunk A, but which reuses terminology or themes from B or C.

## Filtering Synthetic Questions

Synthetic questions can sometimes be unrealistic or off-domain. We can filter them using a process similar to how we filter unrealistic tuples in [Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis). We manually review a subset and rate each question for realism and relevance, then use those labeled examples in a few-shot prompt to another LLM to score the rest. We keep only those deemed realistic.

Here is an example prompt for filtering:

```
You are an AI assistant helping us curate a high-quality dataset of
questions for evaluating a real estate information retrieval system.

Here are examples of realistic and unrealistic user queries we have
manually rated:

Realistic Queries (Good Examples):
- "What are the property taxes for 123 Main St?"
  Rating: 5 — Typical, concise, property-specific.

- "Show me 3-bedroom houses in the North Berkeley area with a backyard."
  Rating: 5 — Natural filter-based query.

Unrealistic Queries (Bad Examples):
- "Tell me about the color of the third brick from the left on the
  chimney of the house that was sold yesterday."
  Rating: 1 — Overly specific and unnatural.

- "If I combine the square footage of all houses listed in zip code
  94704, what is the total?"
  Rating: 2 — Odd aggregation, not representative of real search behavior.

Your Task:
Rate the following generated question for realism on a scale of 1 to 5.
Provide a brief explanation.

Generated Question: "{question_to_evaluate}"

Output Format:
Explanation: [your brief explanation]
Rating: [your 1-5 rating]
```

Note that we use a Likert-style 1-5 rating here because the goal is to roughly rank queries by realism and domain relevance, not to measure failure rates or judge correctness as in LLM-as-Judge settings ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)). This task supports the construction of a “good enough” dataset to begin testing our retrieval pipeline.

## Metrics for Retrieval Quality

Once we have a dataset of queries and their corresponding relevant document chunks, we can evaluate our retriever using standard ranking metrics. The choice of metric depends on what matters for our downstream application. We present four commonly used metrics below.

## Precision@k and Recall@k

Precision@k and Recall@k are the most basic retrieval metrics. They evaluate the quality of the top *k* documents retrieved in response to a query. The value of *k* can vary depending on the query. A factoid question like “What is the property tax for 123 Main St?” might only need *k* =1 or 2, while a synthesis question like “Summarize recent market trends for 3-bedroom houses downtown” might need *k* =5 to 10.

*Precision@k* measures what fraction of the top *k* retrieved documents are actually relevant:

$$
\text{Precision}@ k = \frac{\text{Number of relevant documents in top } k \text{results}}{k}
$$

*Recall@k* measures what fraction of *all* relevant documents for a query appear within the top *k* results:

$$
\text{Recall}@ k = \frac{\text{Number of relevant documents in top } k \text{results}}{\text{Total number of relevant documents for the query}}
$$

Both metrics treat relevance as binary: a document is either relevant or not. If our evaluation dataset uses graded relevance scores (e.g., 0 to 3), we first binarize by applying a threshold (e.g., treat score > 1 as relevant).

In practice, we often care more about recall than precision for the first stage of RAG. Modern LLMs attend more strongly to salient tokens, so they can often work around irrelevant content in the context if the key information is present somewhere. But if that information is missing entirely (low recall), the generator has no way to produce a correct answer. In early retrieval stages, ensuring that relevant content is included is far more important than excluding noise.

###### Tip

When in doubt about which retrieval metric to start with, use Recall@k for the first retrieval stage and NDCG@k for the reranking stage. Use Recall to check whether the right documents made it into the candidate set; use NDCG to check whether they ended up at the top.

## Mean Reciprocal Rank (MRR)

MRR measures how early the first relevant document appears in the ranking. For a single query, the reciprocal rank is $1 / \text{rank}$ where rank is the position of the first relevant document. If no relevant document appears in the top *k* results, the reciprocal rank is 0. MRR is the average across all queries in the evaluation set:

$$
\text{MRR} = \frac{1}{\left|Q\right|} \underset{q \in Q}{\sum} \frac{1}{\text{rank}_{q}}
$$

MRR is especially useful when only one key fact is required to answer a query. Even though the LLM may process multiple retrieved chunks, ranking the correct one first can reduce noise and simplify reasoning. The reason is that LLMs do not attend to their context uniformly. Liu et al. (\[Link to Come\], Liu et al. 2024) ran a multi-document question-answering experiment where the answer was hidden among 20 retrieved documents, and measured accuracy as a function of the answer’s position. They found a U-shaped curve: accuracy was highest when the answer was in position 1 or position 20, and dropped by more than 30 percentage points when the answer was in position 10 (the middle). They called this the *lost in the middle* effect. The implication for RAG is that where a relevant document lands in the retrieval order matters as much as whether it is retrieved at all, which is why MRR (rewarding the top position) is still useful even when we have multiple relevant chunks. For *multi-hop* questions, meaning questions whose answer requires combining facts from two or more retrieved chunks (for example, “Which of our West Berkeley listings has the highest property tax?” requires both the list of West Berkeley listings and the tax information for each), Recall@k or NDCG@k is more informative than MRR.

## Normalized Discounted Cumulative Gain (NDCG@k)

Precision, Recall, and MRR all treat relevance as binary: a document is either relevant or not. But in practice, some documents are more useful than others. For a query like “Summarize market trends for luxury condos downtown,” a recent market analysis report is highly relevant, a general city economic overview is somewhat relevant, and a restaurant guide is irrelevant. *Graded relevance* captures these distinctions by assigning each document a score on a scale, such as 0 (irrelevant), 1 (marginally relevant), 2 (relevant), or 3 (highly relevant).

NDCG@k is designed for this setting. It answers the question: *how well does our ranking place the most relevant documents first?* The metric is built on two intuitions:

More relevant documents should contribute more to the score

A document with relevance 3 matters more than one with relevance 1.

Position matters: earlier is better

A highly relevant document at rank 1 is more valuable than the same document at rank 5, because users (and LLMs) tend to focus on what comes first.

The formula captures both ideas. For each of the top *k* documents, we take its relevance score and divide by the logarithm of its position. The logarithmic discount means the first few positions matter a lot, while later positions contribute less and less:

$$
\text{DCG}@ k = \sum_{i = 1}^{k} \frac{\text{rel}_{i}}{log_{2} \left(i + 1\right)}
$$

Here, $\text{rel}_{i}$ is the graded relevance score of the document at rank *i*. The $log_{2}$ in the denominator is what creates the position discount: rank 1 divides by $log_{2} \left(2\right) = 1$ (no discount), rank 2 divides by $log_{2} \left(3\right) \approx 1.58$, rank 4 divides by $log_{2} \left(5\right) \approx 2.32$, and so on. [Figure 7-3](#fig-dcg-discount) shows how this plays out across rank positions. A document at rank 1 contributes its full relevance score to DCG. A document at rank 2 contributes about 63% as much, and a document at rank 10 contributes only about 29%. Highly relevant documents add a lot more to the total score when they sit near the top.

![dcg discount](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/dcg-discount.svg)

dcg discount

DCG alone is hard to interpret because its value depends on how many relevant documents exist and how relevant they are. To normalize, we compute the *Ideal* DCG (IDCG@k): we take the same retrieved documents, re-sort them in the best possible order (highest relevance first), and compute DCG on that ideal ranking. NDCG@k is then the ratio:

$$
\text{NDCG}@ k = \frac{\text{DCG}@ k}{\text{IDCG}@ k}
$$

A score of 1.0 means our system ranked its documents perfectly. A score of 0.5 means it captured about half the value it could have achieved with better ordering. This normalization makes scores comparable across queries, even when different queries have different numbers of relevant documents.

Why does NDCG@k matter for RAG? Two reasons:

Not all chunks are equally useful

For a query like “Summarize market trends for luxury condos downtown,” a recent market analysis report is highly relevant, while a general city economic overview is only marginally relevant. NDCG@k rewards systems that rank the market report first.

Context windows are finite

If the total size of retrieved documents exceeds the LLM’s context limit, only the first few will be used. NDCG@k ensures the most relevant documents are prioritized.

One caveat to keep in mind is that NDCG@k can produce counterintuitive scores. A system that retrieves only marginally relevant documents but ranks them in perfect order may score highly, while a system that retrieves a highly relevant document but ranks it lower may score worse. Always interpret NDCG@k alongside recall to get the full picture.

## Evaluating and Optimizing Chunking Strategies

Before our retriever can search for relevant content, we divide our documents into smaller pieces called *chunks*. A chunk is the unit of text the retriever can return. If a chunk is too small, a single relevant idea might be split across two chunks, and the retriever may only find one half. If a chunk is too large, it may contain mostly irrelevant text that dilutes the useful content and wastes tokens in the LLM’s context window.

The simplest approach is *fixed-size chunking*: we split each document into consecutive segments of a fixed number of tokens (e.g., 256 tokens each). To avoid cutting sentences or ideas in half at chunk boundaries, we can add *overlap*, where consecutive chunks share some tokens. For example, with a chunk size of 256 and an overlap of 128, the first chunk covers tokens 1-256, the second covers tokens 129-384, and so on. The overlap ensures that content near a boundary appears in at least two chunks, giving the retriever a better chance of finding it.

## Tuning Chunk Size and Overlap

The right chunk size and overlap depend on the structure of our documents and the kinds of questions users ask. There is no single best setting, so we try different combinations and measure which one gives the best retrieval results.

A practical approach is a *grid search*: we pick a few candidate values for chunk size and overlap, re-index the document corpus for each combination, and measure retrieval metrics on our evaluation dataset. [Table 7-1](#tab-chunking-grid-search) shows a hypothetical example of what these results might look like.

In this example, 256 tokens with 50% overlap (128 tokens) yields the best retrieval performance. Notice that adding overlap consistently improves results across all chunk sizes, because it reduces the chance of splitting relevant content across chunk boundaries. Also notice that very large chunks (512 tokens) actually perform worse than medium-sized ones (256 tokens), likely because they include too much irrelevant content alongside the relevant passages.

The specific values in this table are illustrative. In practice, the best configuration depends on your documents and queries. The key takeaway is that chunking is a tunable parameter that can significantly affect retrieval quality, and a systematic search can make a large difference.

## Other Chunking Approaches

Fixed-size chunking is the simplest strategy and a reasonable starting point, but it is one of many options. The right approach depends on the structure of your documents, and it is common to try several and compare them using the retrieval metrics from the previous section.

Semantic or structural chunking

Instead of splitting at a fixed token count, we can split at natural boundaries in the document, such as section headings, paragraph breaks, or topic shifts. This keeps semantically related content in the same chunk. For example, if a report has sections on “Market Trends” and “Pricing,” a structural chunking strategy puts each section in its own chunk, regardless of how many tokens it contains. The chunks will vary in size, but each one will be about a single coherent topic.

Contextual augmentation

We can enrich each chunk with surrounding context before embedding it. For example, we might prepend the document’s title and section headings to a chunk containing “Table 2.” This makes the chunk more self-contained and gives the retriever stronger signals about what it contains.

## Evaluating Generation Quality

With a well-performing retrieval system in place, we turn to evaluating what the LLM does with the retrieved context. Even if retrieval is perfect, the generation step can still fail. We evaluate generation along two dimensions.

The first is *faithfulness*: does the output accurately reflect the information in the retrieved context? In RAG applications, we expect the answer to be grounded in what was retrieved, not in the LLM’s own knowledge. Even if the LLM “knows” the right answer from its pretraining data (sometimes called its *parametric knowledge*, meaning the information baked into the model’s weights), we want it to base its response on the evidence we provided. Faithfulness failures come in three forms:

Hallucinations

the output includes information that is not in the retrieved documents.

Omissions

the output ignores relevant information that *is* in the retrieved documents.

Misinterpretations

the output distorts or inaccurately represents information from the retrieved documents.

The second dimension is *relevance*: does the answer address what the user actually asked? An answer can be perfectly faithful to the context but still miss the point. For example, if the user asks “What are the HOA fees for this property?” and the retrieved context contains both HOA fees and tax information, a response that discusses taxes instead of HOA fees is faithful but not relevant.

We build evaluators for both dimensions using the techniques from [Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators). For faithfulness, an LLM-as-Judge works well: the judge receives both the retrieved context and the generated answer, then checks whether every claim in the answer is supported by the context. For relevance, simpler checks can sometimes suffice. A programmatic evaluator might verify that the answer mentions the specific entity or topic from the query, though for open-ended queries an LLM-as-Judge is usually needed.

A useful technique for debugging faithfulness issues is *context swapping*. We replace the retrieved documents with unrelated ones from a different topic, then run the same query through the pipeline. If the answer stays roughly the same, the LLM is ignoring the retrieved context and relying on its parametric knowledge instead. This is a grounding problem, and it can be subtle because the answer may still happen to be correct. The risk is that when the LLM *does not* already know the answer, it will hallucinate rather than use the retrieved evidence. Context swapping is not a metric to run at scale, but it is a valuable debugging tool for understanding whether our pipeline is actually using its retrieval results.

###### Note

If a context-swap test shows the LLM ignoring retrieved documents, the fix is usually in the prompt, not the retriever. Adding an explicit instruction like “Base your answer only on the provided documents” or “If the documents do not contain the answer, say so” often resolves grounding problems.

## Common Pitfalls

Several pitfalls recur when evaluating RAG pipelines:

Relying only on end-to-end metrics

A single correctness score does not tell us whether retrieval or generation is to blame. To isolate failures, we measure each component independently: Recall@k for retrieval, faithfulness for generation.

Overfitting to synthetic evaluation data

While synthetic data is useful for bootstrapping, it often fails to capture the ambiguity and diversity of real user queries. Many generated questions are too easy or too tightly coupled to specific wording in source documents. Worse, the designated “gold” chunk may not be unique or even optimal. We regularly validate on real queries from logs or human-curated examples. Filtering synthetic data helps, but it does not fully substitute for real-world test sets. Synthetic queries tend to skew toward extractive answers and miss multi-hop or judgment-based questions.

###### Warning

Synthetic QA pairs often mirror the exact vocabulary of the source chunk, making retrieval artificially easy. If your Recall@k looks great on synthetic data but users still get bad answers, supplement with 20 to 30 real user queries from logs before drawing conclusions.

Choosing the wrong metric

If the LLM needs a single fact, MRR may suffice. If it needs to synthesize multiple chunks, Recall@k or NDCG@k is a better fit. Choosing the wrong metric leads us to optimize for behaviors that do not actually improve output quality.

Ignoring chunking as a variable

Chunks that are too small scatter relevant information. Chunks that are too large contain irrelevant noise. Retrieval metrics like Recall@k can vary significantly based on chunking alone, even with the same retriever model.

Evaluating generation without checking grounding

Fluency and overlap with a reference answer are not enough. A response that sounds correct but contradicts the retrieved evidence undermines the entire purpose of RAG. We need context-sensitive metrics that verify whether the generation aligns with what was retrieved.
