## Chapter 6. Evaluating Multi-Turn Conversations

Until now, we have focused on evaluating interactions where the user sends one message and the agent sends one response back. We call that a *single-turn* interaction, meaning one exchange between the user and the agent. Many applications involve *multi-turn* conversations, where the user and agent go back and forth multiple times. Each exchange (one user message and the agent’s response) is a *turn*. A full conversation from start to finish is a *session*.

In multi-turn conversations, the agent has to maintain context across turns, follow instructions over time, and respond coherently as the conversation develops. This creates new evaluation challenges that single-turn methods do not cover.

In this chapter, you will learn:

- How to evaluate at the session, turn, and coherence levels
- When to isolate failures as single-turn problems versus genuinely multi-turn issues
- How to use perturbation testing to probe robustness
- How to build session-level evaluators before investing in turn-level analysis

The core evaluation lifecycle, Analyze, Measure, Improve ([Figure 1-2](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch01.html#fig-eval-lifecycle)), still applies, and the key principles from previous chapters still hold. We begin with qualitative error analysis. We favor simple, often binary evaluation criteria. But multi-turn interactions add complexity in what we measure and how we collect meaningful evaluation data.

Multi-turn is also where otherwise strong models tend to fall apart. Laban et al. (\[Link to Come\], Laban et al. 2025) ran over 200,000 simulated conversations against several of the leading LLMs (both commercial ones like GPT-4 and open-source ones like Llama) on six different tasks, including coding, math word problems, and summarization. They compared two setups for each task: the single-turn setup, where the user gives all the information at once, and the multi-turn setup, where the user drips out the same information over several messages. Accuracy dropped by an average of 39% in the multi-turn setup. The interesting finding is *why*. The authors split the drop into two parts: a small decline in the model’s raw ability (the model is still roughly as smart as it was in single-turn) and a much larger increase in unreliability. What they mean by unreliability is that the model tends to make an early guess after the first user message, commit to it, and then fail to revise that guess when the user provides new information in later messages. Once the model is on the wrong track, it stays there. This is worth keeping in mind: when multi-turn conversations in our own agents break down, it is usually not that the underlying model got worse. It is that the model committed to an answer too early and never came back to fix it.

## Evaluating at Different Levels

Multi-turn evaluation operates at three distinct levels. These levels are not mutually exclusive. Rather, they give us different lenses on the same conversation. In practice, they form a drill-down workflow: we start broad at the session level, then narrow into specific turns and coherence issues when we find failures.

## Session Level

At the session level, we ask whether the full conversation achieves the user’s intended goal. This assessment is often binary (Pass or Fail) and gives us a high-level view of system effectiveness.[^1] For example, if a peer feedback assistant ends a session without eliciting any useful feedback from the user, we might mark the entire session as a failure, even if individual turns were well-formed. The overall task was not accomplished.

Session-level evaluation is where we recommend starting. It provides the broadest performance signal with the least overhead, and it directly answers the question that matters most: did the system do what the user needed?

###### Tip

Start with session-level evaluation and resist the urge to score every turn. A single Pass/Fail label per conversation tells you how often the system works. Turn-level analysis comes later, only for sessions that have already been flagged as failures.

## Turn Level

Turn-level evaluation is a diagnostic tool, not a primary evaluation strategy. We use it to pinpoint *where* things went wrong within a session that has already been flagged as a failure.

Once we identify a failing session, we walk through its individual turns and ask the same questions we would in single-turn evaluation. Is this response relevant? Is it correct? Is the tone appropriate? The goal is to find the specific turn where the conversation went off track, which tells us what to fix.

## Conversational Coherence and Memory

The third level focuses on properties that only emerge across multiple turns. Within a session, we check whether the assistant remembers what the user said earlier. Across sessions (for applications that persist state), we examine whether the assistant appropriately retains knowledge through stored summaries or memory tools.

Coherence failures are subtle. They often only surface after several turns and can be difficult to catch in standard single-turn evaluations. Common examples include:

Forgetting stated preferences

The user specifies a constraint early in the conversation, and the assistant ignores it in a later turn.

Contradicting earlier responses

The assistant provides conflicting information across turns.

Losing track of the task

In a multi-step workflow, the assistant loses context about which steps have been completed.

## Practical Strategies for Multi-Turn Evaluation

## Collecting Traces

We begin by collecting an initial dataset of multi-turn traces. A lightweight chat interface is often enough. Team members simulate user behavior and engage in 10 to 15 tasks each, trying out different intents and personas. With just a few participants, we can quickly gather 100 or more diverse traces.

We then manually review these conversations, collecting examples of both successes and failures, and asking the basic questions you would ask of any trace: whether the assistant accomplished the user’s goal, whether it followed instructions throughout, and where things went wrong if they did.

## Isolating Failures

When we find failures in multi-turn traces, a critical first step is determining whether the failure is *actually* multi-turn in nature. Many failures that surface during a conversation are, at their core, single-turn problems. Isolating this distinction saves significant debugging effort.

The technique is straightforward: take the failing turn and try to reproduce the issue with a single-turn prompt that includes all the relevant context. Consider the following example, where a shopping assistant gives incorrect information on the fourth turn of a conversation:

##### Example 6-1. A multi-turn failure that reduces to a single-turn problem.

```
User: Hi, I want to know about returns.

Bot: Sure, what product are you asking about?

User: The X1000.

Bot: The return window for X1000 is 15 days. (Incorrect; it should be 30.)
```

We can test whether this is truly a multi-turn issue by condensing it into a single prompt: “What is the return window for product X1000?” If the LLM still responds with “15 days,” the failure is not caused by the conversational context. It is a retrieval or grounding issue, and we can debug it using the single-turn techniques from earlier chapters.

But not all failures simplify this way. Some are inherently tied to the conversational setup:

##### Example 6-2. A failure that is inherently multi-turn: the assistant forgets a stated preference.

```
User: I'm looking for a movie.

Bot: Great! Any preferred genre?

User: I love sci-fi.

Bot: Okay, sci-fi. Any actors you like?

User: Not particularly.

Bot: How about _The Love Llama_, a heartwarming romantic comedy?
```

Here, the assistant clearly forgot the “sci-fi” constraint.[^2] There is no way to reproduce this as a single-turn problem because the failure is precisely about maintaining context across turns.

To study it systematically, we can truncate the trace before the failing turn and sample the LLM multiple times to observe how often it retains versus drops the user’s stated preference. We can construct a dataset of these “N-1 turn” prompts, either by extracting prefixes from real conversations or generating them synthetically, to test short-term memory and consistency at scale.

## Perturbation Testing

Once we have a set of multi-turn traces that pass (the agent handles them correctly), we can test how robust the agent is by making small, deliberate changes to those traces and checking whether the agent still handles them. This is *perturbation testing*: we take a passing conversation, modify one thing, and see if the agent breaks.

The kinds of modifications we can try include:

Changing the user’s goal mid-conversation

For example, starting from [Example 6-2](#ex_movie_memory), we could insert “Actually, my partner hates sci-fi. Can we do a thriller instead?” after the user originally asked for sci-fi. If the agent still recommends sci-fi, it has failed to update its understanding.

Adding ambiguity

We can rephrase a clear user message to be vague or underspecified, and see whether the agent asks for clarification or guesses incorrectly.

Contradicting the agent

If the agent suggests something, we can have the user say “no, that’s wrong” and check whether the agent corrects course or doubles down.

Perturbation testing is useful because it generates failing traces from known-good ones without waiting for production failures to occur. It is especially good at catching brittleness: an agent that works on the exact conversations in its test set but fails when anything changes slightly.

## Automated Evaluation of Multi-Turn Traces

Once we have identified clear failure types through manual review, we can build automated evaluators using the same techniques from [Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators). These may be LLM-as-Judge models, programmatic filters, or a hybrid of both.

The key question is *what level to evaluate at.* For most systems, we recommend starting with session-level evaluators. A session-level LLM-as-Judge receives the full conversation and issues a Pass/Fail verdict on whether the user’s goal was met. This is the highest-leverage evaluator to build first because it directly measures what matters.

Turn-level evaluators are useful for specific, well-defined failure modes. For example:

- A programmatic check that verifies the assistant never contradicts information it provided in a previous turn.
- An LLM-as-Judge that evaluates whether each tool call in the conversation was justified by the preceding user message.
- A coherence check that extracts user-stated constraints and verifies they are respected in the assistant’s final recommendation.

Not every evaluator needs to assess every turn. In fact, for many systems, we only need turn-level analysis when debugging specific paths. Session-level evaluation provides a broader performance signal with less overhead.

## Addressing Common Pitfalls

There are several pitfalls specific to multi-turn evaluation to watch for.

Failures that correlate with conversation length

Many systems behave well in the first two or three turns but then degrade. They may forget context, ignore instructions, or contradict earlier responses. Our test sets should include conversations of varying lengths to detect these position-dependent failures. If we only test short conversations, we will miss problems that real users encounter in longer sessions.

Over-investing in turn-level evaluation

It is tempting to build evaluators for every turn in a conversation, but this quickly becomes expensive and noisy. Most of the signal comes from session-level evaluation. We reserve granular analysis for focused debugging: identify failing sessions first, then drill into a handful of representative traces to find root causes.

Confusing multi-turn failures with single-turn failures

As illustrated in [Example 6-1](#ex_shopping_returns), many failures that appear during multi-turn conversations are actually single-turn problems in disguise. Always attempt to isolate the failure before building multi-turn-specific evaluators. This avoids over-engineering solutions for problems that have simpler fixes.

## Putting It Together

Evaluating multi-turn conversations extends the single-turn techniques from earlier chapters to account for memory, flow, and long-term success. We start broad at the session level, drill into individual turns when we find failures, and check for coherence issues that only emerge across multiple exchanges. The key practical techniques are isolating whether a failure is truly multi-turn, perturbation testing to probe robustness, and building session-level evaluators before investing in turn-level analysis.
