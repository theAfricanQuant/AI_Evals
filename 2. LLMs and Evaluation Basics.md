## Components of LLM Applications

Most LLM applications can be described in terms of a few recurring components. Each of these components brings different capabilities, and each comes with its own characteristic failure modes to analyze. We will cover these components in increasing order of complexity, showing how they build on one another to create sophisticated applications.

Before diving into the components, we need to understand how we interact with LLMs programmatically. All the code examples in this chapter use [*LiteLLM*](https://github.com/BerriAI/litellm), a popular Python library that provides a unified interface for calling different LLM APIs (e.g., OpenAI, Anthropic, Google Gemini, etc.) with consistent syntax.

LLM APIs expect input as a *list of message objects*, where each message has two fields: `role` and `content`. The `role` field specifies who is speaking and can be one of three values:

`system`

Sets the overall behavior and context for the assistant (e.g., “You are a helpful assistant that summarizes emails”). This is optional but helps establish consistent behavior across requests.

`user`

Represents input from the human or application making the request. This is where you provide the actual task or query.

assistant\`

Represents previous responses from the LLM. You include these when maintaining conversation history across multiple turns.

`tool`

Used to pass the results of a tool invocation back to the LLM. Not supported by all models, but used with LLMs that support tool calling (which we will discuss later in this chapter).

For a single request, you typically send a list with one or two messages: an optional `system` message to set context, and a `user` message with your query. For multi-turn conversations, you append each exchange to the list as alternating `user` and `assistant` messages.

###### Tip

When debugging conversation issues, check that you’re alternating `user` and `assistant` messages correctly. Mismatched roles are a common source of errors.

For each component below, we present an example code snippet that pertains to the following email summarizer example.

> Imagine you are building a simple *email summarizer* for your organization. It should take an incoming email and produce a short summary that includes the sender’s name and their key requests.

## Single-step LLM calls

The simplest component is a single call to a model. You provide an input prompt, the model generates a response, and that response is passed straight back to the user or to the next stage in your pipeline.

For the email summarizer, this could be one prompt that takes the body of an email and asks the model to extract the sender’s name and summarize the requests. In code, a single-step call might look like this:

```
from litellm import completion

response = completion(
    model="gpt-5",
    messages=[
        {
            "role": "system",
            "content": "You are an assistant that summarizes emails."
        },
        {
            "role": "user",
            "content": "Extract the sender's name and summarize the key requests:\n\n"
                      + email_text
        }
    ]
)

print(response["choices"][0]["message"]["content"])
# Example output:
# "Sender: Alice Johnson
#  Key requests:
#  - Reset her account password
#  - Verify email on file"
```

Single LLM calls like this are a natural starting point when building applications. But modern applications often combine additional components: e.g., retrieval to bring in related messages, tools to query internal systems, or agent loops that coordinate multiple steps. Each component brings new capabilities, but also introduces its own potential failure modes.

## Conversations

Many applications don’t stop at a single request–response exchange. They allow the user and the model to interact over multiple turns. This conversational setting is what most people associate with chatbots, customer-support assistants, or copilots.

In our email example, instead of just producing a summary given a single user message, the system could support follow-up questions:

```
User: Summarize the email.
System: Sender: Alice Johnson. Key requests: reset her account password; verify email on file.
User: Does she mention her preferred contact method?
System: Yes. She asks to be contacted by phone.
```

Technically, a conversation is just a series of LLM calls where the prompt includes the full dialogue history (or at least the recent turns). Here is a minimal illustration:

```
from litellm import completion

messages = [
    {
        "role": "system",
        "content": ("You are an assistant that summarizes and "
                    "answers questions about emails.")
    },
    {"role": "user", "content": "Summarize this email:\n\n" + email_text}
]

response1 = completion(model="gpt-5", messages=messages)
print(response1["choices"][0]["message"]["content"])
# "Sender: Alice Johnson. Key requests: reset her account password; verify email on file."

# Add the model's reply to the conversation and continue
messages.append({
    "role": "assistant",
    "content": response1["choices"][0]["message"]["content"]
})
messages.append({
    "role": "user",
    "content": "Does she mention her preferred contact method?"
})

response2 = completion(model="gpt-5", messages=messages)
print(response2["choices"][0]["message"]["content"])
# "Yes. She asks to be contacted by phone."
```

Conversation brings the system closer to how people naturally interact with assistants. But it also introduces new design choices: how much dialogue history to keep, how to manage context length, and how to ensure consistency across turns. These are all aspects we will return to when we discuss evaluation.

## Retrieval

Sometimes, the LLM needs background knowledge that isn’t in the immediate input. Retrieval-augmented generation (RAG) is a common pattern: the system searches a knowledge base or document store, pulls in relevant passages, and then gives both the query and the retrieved context to the model.

In the email summarizer, retrieval might bring in prior messages from the same sender or related support tickets. That way, the model can understand the new message in light of past correspondence—for example, recognizing that *“I still can’t log in”* refers to an ongoing password reset issue.

There are two common approaches to retrieval:

Keyword-based methods (for example, BM25)

These rank documents by the amount of word overlap with the query. They are fast and work well when domain terminology is stable.

Embedding-based methods

These represent queries and documents as vectors and rank them by semantic similarity. They can match meaning even when wording differs (“reset my login” vs. “can’t sign in”).

A typical pipeline has two steps: (1) search for relevant items, then (2) insert those items into the LLM prompt.

```
# Small archive of past support emails
past_emails = [
    "Ticket #4521: Please reset my password. I cannot log in.",
    "Ticket #4605: Could you verify my email address on file?",
    "Ticket #4710: I need help updating my phone number."
]

# Embedding-based retrieval
from litellm import embedding, completion
import numpy as np

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

corpus_embeddings = [
    embedding(
        model="text-embedding-3-small",
        input=doc
    )["data"][0]["embedding"]
    for doc in past_emails
]

query_embedding = embedding(
    model="text-embedding-3-small",
    input=email_text
)["data"][0]["embedding"]
scores = [cosine_similarity(query_embedding, e) for e in corpus_embeddings]
retrieved = past_emails[int(np.argmax(scores))]

# Combine retrieved context with the new email
messages = [
    {
        "role": "system",
        "content": "You are an assistant that summarizes emails with "
                    "context."
    },
    {
        "role": "user",
        "content": (f"Email:\n{email_text}\n\n"
                    f"Related past email:\n{retrieved}")
    }
]

response = completion(model="gpt-5", messages=messages)
print(response["choices"][0]["message"]["content"])
# Example output:
# "Sender: Alice Johnson.
#  Key requests: reset her account password and confirm contact information.
#  Context: this continues a previous unresolved login issue."
```

Keyword-based retrieval could be swapped in here using a library like `whoosh` or `elasticsearch`, returning the top BM25 match instead of computing embeddings.

Whichever method you choose, retrieval changes the system’s behavior: the quality of the output now depends both on what gets retrieved and on how the model uses it. These are issues we’ll return to when we discuss evaluation of multi-component pipelines.

## Tools

Some tasks are better handled by software than by the model itself. Think about doing exact math, pulling information from a system of record, or reformatting something like a date or a phone number. In these cases, it is easier and more reliable to let the model call a tool instead of trying to produce the result on its own.

A tool is basically a Python function. We describe the function to the model, along with the arguments it expects, so the model knows how to invoke it. When the model calls the tool, our runtime executes the function and feeds the result back into the conversation.

In the email summarizer, suppose the sender includes a callback number like: *“Call me at (415) 555-9021 ext. 7.”* If you want to store this in your Customer Relationship Management (CRM) or pass it into an automated dialer, you’ll need the number in a standard format. Rather than relying on the model to rewrite phone numbers consistently, you can give it access to a `normalize_phone` tool that always produces the same output format.

```
from litellm import completion
import json
import phonenumbers

# Define the tool as a Python function
def normalize_phone(number: str):
    parsed = phonenumbers.parse(number, "US")
    return phonenumbers.format_number(
        parsed, phonenumbers.PhoneNumberFormat.E164
    )

# Tell the model what the tool is and how to call it
tools = [
    {
        "type": "function",
        "function": {
            "name": "normalize_phone",
            "description": "Convert a phone number to "
                           "standardized E.164 format",
            "parameters": {
                "type": "object",
                "properties": {"number": {"type": "string"}},
                "required": ["number"]
            }
        }
    }
]

messages = [
    {
        "role": "system",
        "content": "You summarize emails and may call tools when helpful."
    },
    {"role": "user", "content": f"Summarize this email:\n\n{email_text}"}
]

resp = completion(model="gpt-5", messages=messages, tools=tools)
msg = resp["choices"][0]["message"]

# If the model calls the tool, run it and send back the result
if "tool_calls" in msg:
    for call in msg["tool_calls"]:
        if call["function"]["name"] == "normalize_phone":
            args = json.loads(call["function"]["arguments"])
            result = normalize_phone(**args)
            messages.append({
                "role": "assistant",
                "tool_call_id": call["id"],
                "name": "normalize_phone",
                "content": json.dumps(result)
            })

# Continue the conversation until the model produces a final summary
resp2 = completion(model="gpt-5", messages=messages, tools=tools)
print(resp2["choices"][0]["message"]["content"])
# Example:
# "Sender: Alice Johnson. Key requests: reset her account password.
#  Preferred contact: +14155559021"
```

This approach is not limited to small utilities. In practice, applications often expose tools such as calculators, calendar lookups, search engines, or CRM APIs. These let the model handle parts of the task that require precision, data access, or integration with existing systems.

###### Warning

Tools give LLMs access to real actions. Always validate tool inputs and consider the security implications before allowing an LLM to call functions that modify data or external systems.

###### Note

Retrieval can also be seen as just another tool. Instead of returning a phone number, the function returns a set of documents given a query. We treat it separately here only because retrieval is such a common building block in modern applications.

A recent effort to make this easier is the [*Model Context Protocol (MCP)*](https://modelcontextprotocol.io/docs/getting-started/intro). MCP defines a standard way for a tool server to describe available functions—including their names, arguments, and authentication requirements—and for a client to discover and call them. Instead of writing custom glue code for every service, you can point your application at an MCP server and the model immediately has a catalog of tools it can use.

## Agents

So far we have seen single calls, conversations, retrieval, and tools as separate components. These are all agents in the broad sense we defined in [“What Is an “Agent”?”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch01.html#sec_terminology), but they are relatively simple. The most complex pattern is an *agent loop*. In this pattern, the LLM receives the current state, decides what action to take, executes it, observes the result, and repeats until the task is complete. The defining feature is that the model decides each step as it goes, rather than following a predetermined sequence.

In the email summarizer, an agent might start by reading the new message and deciding that more context is needed. It retrieves past correspondence from the same sender, looks at the result, and then chooses to call a tool to normalize a callback number. Only after those steps does it decide that it now has enough information to produce a final summary. What makes this an agent is not the specific sequence of actions, but the fact that the model is deciding them one by one as it goes.

```
# Minimal sketch of an agent loop
from litellm import completion

messages = [
    {
        "role": "system",
        "content": ("You are an agent that can retrieve past emails, "
                    "call tools, and summarize.")
    },
    {
        "role": "user",
        "content": f"Summarize this new email:\n\n{email_text}"
    }
]

for step in range(10):  # cap the number of steps
    resp = completion(model="gpt-5", messages=messages, tools=tools)
    msg = resp["choices"][0]["message"]

    # If the model requests a tool, run it and append the result
    if "tool_calls" in msg:
        # (execute retrieval or tool functions here)
        messages.append({
            "role": "assistant",
            "content": "Tool result goes here"
        })
        continue

    # If the model produces a final answer, stop
    if msg.get("content"):
        print("Final output:", msg["content"])
        break
```

Frameworks like LangChain, LlamaIndex, and AutoGPT wrap this pattern with additional features such as memory, planning strategies, and error handling. When reading blog posts or papers about agents, it is easy to feel overwhelmed with jargon and seemingly complex ideas. But the idea is simple: an agent is just repeated LLM calls that decide, step by step, whether to generate text, retrieve information, call a tool, or stop when the task is complete.

###### Note

Agent loops can, in theory, run indefinitely if not bounded. Always include a maximum step count (as shown in the example with `range(10)`) and consider implementing timeouts in production systems.

## Fundamentals of Prompting

So far we have covered the architectural components of an LLM agent, including single calls, conversations, retrieval, tools, and the agent loop. Another set of fundamentals is how to write the prompts that drive each of these components. A good prompt is specific enough to guide the model and consistent enough to give predictable outputs. Over time you will refine it, but a strong starting point has a few recurring pieces.

## Prompts for Single LLM Calls

A good first draft prompt usually includes:

Role

Tell the model who it is meant to be. This keeps it anchored in the right domain.

Objective

State clearly what the task is and what success looks like.

Instructions

Spell out do’s and don’ts. For example, if you need three bullet points, say so. If quoted text should be excluded, make that explicit.

Context

Provide the data the model should act on, like the email, the document, or any other text snippets. Without context, it can only guess.

Reasoning

For harder tasks, you can ask the model to think step by step, or explain how the model should “think” before returning the answer.

Output format

Describe how the answer should be structured so it’s easy to consume downstream.

Examples

Optional but powerful. A short input–output pair shows format, style, and level of detail.

Delimiters

Use section headers, code fences, or tags to keep instructions, context, and examples separate.

In practice, you typically organize these elements into a *prompt template* —a reusable structure with placeholders for variable content that will be filled in at runtime. For example, the `[PASTE EMAIL TEXT HERE]` placeholder would be replaced with the actual email text when the application runs. Using templates makes prompts easier to maintain, debug, and version control, since you can modify specific sections without rewriting the entire prompt each time.

The following example shows how the aforementioned elements come together in a prompt template for our email summarizer.

##### Example 2-1. Example: Prompt template for email summarizer

```
### Role
You are an assistant for our internal support team.

### Objective
Extract the sender’s name and summarize the key requests in an incoming email.

### Instructions
- Produce exactly three concise bullet points for the requests.
- Do not include quoted text from prior threads or signatures.
- Keep the tone plain and professional.

### Context
[PASTE EMAIL TEXT HERE]

### Reasoning
Think through the steps needed to extract the sender and requests,
but return only the final formatted output.

### Output format
- Sender: <name>
- Requests:
  - <bullet 1>
  - <bullet 2>
  - <bullet 3>

### Example
Input: "My account was locked after travel. Please reset it and call me at (415) 555-9021."
Output:
- Sender: Alice Johnson
- Requests:
  - Reset account access
  - Call back at (415) 555-9021
```

Another benefit of using a template is that it makes prompts easier to refine. Suppose you discover the model sometimes includes quoted email threads in its summaries, and you don’t want the summaries to include too much information from previous emails in a thread. With a structured template, you know exactly where to fix this; add a line in the instructions section that says, “Do not include quoted text from prior threads.” Or imagine you realize the summaries don’t always include a clear call to action for the support agent. You can add a new field in the format section, for example, “Next action for agent: \<short instruction>.” Overall, instead of piling ad-hoc notes into one long block, the template keeps changes organized and easy to maintain.

###### Tip

Store your prompt templates as separate files or configuration rather than hardcoding them. This makes it easier to version, test, and iterate on prompts without changing application code.

## Retrieval Fundamentals

When implementing retrieval for your application, we recommend starting with keyword search. It is fast to set up, easy to interpret, and often a very strong baseline. With keyword methods like BM25, you can see exactly why a document was retrieved, because the query terms overlap with it. This transparency makes debugging straightforward, and in many domains with stable vocabulary (like support tickets), keyword search performs surprisingly well.

Here is a toy example using the `rank_bm25` library on a small list of past support emails:

```
from rank_bm25 import BM25Okapi
import numpy as np

# Small archive of past emails
past_emails = [
    "Ticket #4521: Please reset my password. I cannot log in.",
    "Ticket #4605: Could you verify my email address on file?",
    "Ticket #4710: I need help updating my phone number."
]

# Build BM25 index
tokenized_corpus = [doc.lower().split() for doc in past_emails]
bm25 = BM25Okapi(tokenized_corpus)

query = "I still can’t log in."
tokenized_query = query.lower().split()

# Score and select the best match
scores = bm25.get_scores(tokenized_query)
best_doc = past_emails[int(np.argmax(scores))]

print(best_doc)
# Example output:
# "Ticket #4521: Please reset my password. I cannot log in."
```

This is only a toy demonstration. In practice, your corpus may be thousands of emails or tickets stored in a database, and you would use the database’s own retrieval features or a dedicated search library to handle indexing and ranking. The important part is that you begin with a simple, interpretable baseline. From there, if you find it misses relevant cases, you can move on to more flexible or complex methods such as embedding search.

## Tools and Agents

When you add tools to an application for the first time, the main step is to describe them clearly to the model. Most modern APIs expect a specification in the style of OpenAPI: a function name, a short description, and a JSON schema for its arguments and return type. It is worth being precise here: write descriptions that explain exactly what the function does, define arguments unambiguously, and think through edge cases. For example, if a number must be a string, say so. If the tool only works for U.S. phone numbers, make that explicit. The clearer the specification, the less room there is for the model to make mistakes while using the tool.

Here is an example tool spec for normalizing phone numbers:

```
{
  "type": "function",
  "function": {
    "name": "normalize_phone",
    "description": "Convert a phone number to standardized E.164 format",
    "parameters": {
      "type": "object",
      "properties": {
        "number": {
          "type": "string",
          "description": "Phone number to normalize, assumed to be US "
                         "if no country code is provided"
        }
      },
      "required": ["number"]
    }
  }
}
```

A first-pass tool prompt can reuse the same template we developed earlier (role, objective, context, instructions, format). The only addition is a section that lists the available tools and explains when they should be used. For example: “You summarize emails. You may call `normalize_phone` whenever a phone number is present. Always include the tool’s result in the final summary.” Combined with the tool spec, this is enough to get a simple tool-enabled pipeline running.

Once you have prompts, retrieval, and tools in place, you can combine them into an *agent*. An agent is simply a system that loops through the following cycle: the model reasons about the current state, decides whether to act (by calling a tool or retrieving context), observes the result, and continues until it produces a final answer. This pattern is often called *ReAct* (“Reason + Act”) Yao 2023. The following example shows a ReAct-style agent prompt for our email summarizer.

##### Example 2-2. Example: Agent prompt (ReAct-style) for email summarizer

```
### Role
You are an agent that helps summarize support emails.

### Objective
Read a new email, use retrieval and tools when helpful, and produce a final summary for the support team.

### Instructions
- You may retrieve past tickets if needed.
- You may call \`normalize_phone\` when a phone number is present.
- Work step by step. At each step, decide on one action
(retrieve, call a tool, or stop with a final answer).
- After you take an Action, you will receive an Observation,
with the result. Use it to decide your next step.
- End with a final answer in the specified format.
- If the user’s request is ambiguous, [choose one]:
**(a)** ask a clarifying question before proceeding;
**(b)** infer the most likely intent and continue.

### Reasoning (ReAct pattern)
Follow the Thought → Action → Observation cycle:
- **Thought:** (optional, for development) a brief statement of what you intend to do.
- **Action:** the tool to call, with JSON arguments.
- **Observation:** will be provided after each action.
- Repeat until you produce the final answer.

### Output format (for Final)
Final answer:
- Sender: <name>
- Requests:
  - <bullet 1>
  - <bullet 2>
  - <bullet 3>
- Phone: <normalized number if present>

### Step format example
Thought: I should check prior tickets for context.
Action: retrieve_tickets
Args: {"query": "can’t log in; password reset", "sender": "<sender_email>"}

Observation: [{"id":"4521","text":"Please reset my password. I cannot log in."}]

Thought: A phone number is present; I will normalize it.
Action: normalize_phone
Args: {"number": "(415) 555-9021 ext. 7"}

Observation: "+14155559021"

Thought: I have enough information to write the summary.
Final:
- Sender: Alice Johnson
- Requests:
  - Reset account access
  - Verify email on file
  - Call back at +14155559021
```

One important design choice in building an agent is how much freedom it should have. For example, if you want it to be cautious and avoid guessing on behalf of the user, include some instruction such as: *“If anything is ambiguous, always ask the user to clarify before proceeding.”* If you want it to be more autonomous, instead say: *“If anything is ambiguous, infer the most likely intent and continue.”* Making this decision explicit in the prompt will make the agent’s behavior more predictable and easier to evaluate later.

## Evaluation Setups

There are a wide variety of evaluation setups described in the literature and used in practice. We can bucket them all into two types of high-level questions: *“Is this system good enough to ship?”* and *“Which of these options works better?”* The first question requires *absolute evaluation*, or judging whether your system meets some standard of correctness. The second requires *comparative evaluation*, or deciding which of several alternatives performs best.

## Absolute Evaluation

This is where most teams start. You’ve built a system—say, the email summarizer with its first draft prompt—and you need to know if it’s good enough to use. That means defining what “good enough” actually means, then checking whether your outputs meet that bar.

In the literature, metrics for absolute evaluation are often grouped into one of the following:

Reference-based evaluation

You compare the model’s output against labeled data, often called “gold” summaries or ground truth. For the email summarizer, you’d prepare a dataset of emails with human-written summaries, then score each model output for exact match, overlap with the reference, or semantic similarity. This approach is appealing because it gives clear right-wrong comparisons. But it has two problems: labeled data is expensive to create, and many tasks have multiple valid outputs. One good summary might say *“Reset password; confirm email on file”* while an equally valid one says *“Help me log in; verify my registered address.”* Scoring against only one reference penalizes perfectly good outputs. We recommend reference-based methods only when there’s genuinely a single correct answer, like verifying whether a field was extracted correctly.

Reference-free evaluation

Here, you check the output against criteria you define, without needing a gold answer. For the email summarizer, you might verify that the output includes a *“Sender:”* field, produces exactly three bullet points, and avoids quoted text from previous threads. You might also check that it doesn’t invent details that aren’t explicitly mentioned in the email. Correctness is usually a set of criteria like this—format, completeness, factuality—rather than matching a single right answer. You can automate these checks with rules or use another model as a judge. Most teams don’t have labeled datasets for their specific application, so reference-free evaluation is usually the only practical option.

###### Note

This book focuses on reference-free evaluation methods. Most teams don’t have the time or resources to create labeled datasets for their specific application, so reference-free approaches are the practical starting point. In Chapter 3, we’ll show you how to systematically identify what to evaluate.

## Comparative Evaluation

Once you have something working reasonably well, you might want to compare alternatives, such as different prompts, models, or retrieval methods. Now the question isn’t “is this correct enough?” but “which of these is better?” omparative evaluation typically takes one of these forms:

Pairwise comparison

For each input, you generate two outputs—one from prompt A, and one from prompt B. An evaluator (human or model) picks which one better meets some criterion. For the email summarizer, the question might be: “Which output more accurately captures the sender’s requests without adding extra details?”

Ranking and leaderboards

Instead of comparing just two outputs, evaluators rank three or more options for the same input. Aggregate these rankings across many inputs and you get system-level scores—a leaderboard. Public benchmarks like [LMArena](https://lmarena.ai/) use this format to compare different AI models. Some companies maintain internal leaderboards to track which prompt, model, or configuration performs best.

###### Note

We won’t cover comparative evaluation in detail in this book. Most teams don’t run these regularly, because comparative evaluation is closer to A/B testing and only makes sense once you have a working system and multiple variants worth comparing. The real bottleneck is getting a single configuration to work reliably first, which is why we focus on absolute evaluation.

## Putting It Together

You now have the building blocks for an LLM agent. These include single LLM calls, conversations, retrieval, tools, and agent loops. You understand the two main evaluation approaches: absolute evaluation (is this good enough?) and comparative evaluation (which is better?). You’ve seen how to structure prompts with templates.

When you run your prototype on real data, you’ll find problems. The model might interpret instructions differently across inputs. Retrieval might return irrelevant documents. Output quality might vary unpredictably. These problems are your starting point for evaluation.

The next chapter shows you how to analyze these problems systematically. You’ll learn how to collect representative examples, categorize different types of failures, and distinguish between two root causes: specification failures (where your prompt was unclear or incomplete) and generalization failures (where the model behaves inconsistently despite clear instructions). This systematic error analysis is the foundation for everything that follows in the book.
