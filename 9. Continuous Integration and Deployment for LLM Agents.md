## Chapter 9. Continuous Integration and Deployment for LLM Agents

In July 2023, researchers at Stanford and Berkeley published a study tracking GPT-4’s behavior over time (\[Link to Come\], Chen et al. 2024). They ran the same math tasks on the GPT-4 API in March 2023 and again in June 2023, and found that accuracy on identifying prime numbers dropped from 84% to 51%. OpenAI had updated the model behind the `gpt-4` API endpoint without any announcement. Teams that had been calling `gpt-4` in production woke up one morning with a model that behaved differently on their tasks, and they had no way of knowing until users complained.

This is the kind of problem that continuous evaluation is designed to catch. Getting an LLM agent to work well once is hard enough. Keeping it working over time is a different challenge entirely. User needs change, data distributions shift, and model providers push updates without warning. A nightly regression suite that re-evaluated our prompts against a fixed set of test cases would have caught that accuracy drop before it reached production.

In this chapter, we cover how to build that kind of safety net. We introduce two practices borrowed from software engineering: *continuous integration (CI)* and *continuous deployment (CD)*. By the end, you will understand:

- How to build a *golden dataset* of curated test cases that catches regressions before they ship.
- How to monitor real-world performance in production using the evaluators from [Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators).
- How CI and CD connect into a continuous improvement loop that keeps your agent healthy over time.
- When and how to revisit your prompts as foundation models improve.

Adapting CI/CD for LLM systems is not a straightforward translation from traditional software or even from earlier MLOps. LLM agents have unique properties that change how we test and monitor them. [Table 9-1](#tab_ci_cd_contrast) summarizes two key concepts that organize the rest of this chapter.

| Role | What it does | Example |
| --- | --- | --- |
| **CI: Unit tests for known unknowns** | Guards against regressions on failure modes we have already identified. Runs before deployment. | After editing the prompt for our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), CI checks confirm that the “Location Ambiguity” bug we fixed last month has not reappeared. |
| **CD: Online monitoring for unknown unknowns** | Tracks system behavior on live traffic. Surfaces new failure modes we did not anticipate during development. | A new neighborhood-targeting feature causes the LLM to confuse “West Berkeley” with “Berkeley West” (a non-existent area). Online monitoring detects the spike in location errors before too many users are affected. |

These two roles are complementary. We use CI to catch what we know about, and CD to catch what we do not yet know about. Neither is sufficient alone.

LLM agents also differ from traditional ML systems in ways that affect how we implement CI/CD. [Table 9-2](#tab_llm_vs_mlops) summarizes the key differences.

| Aspect | Traditional ML | LLM Agents |
| --- | --- | --- |
| Training data | Large labeled datasets. CI validates against substantial test sets after retraining. | Few labeled examples, curated around known failure modes. Core logic lives in prompts and the foundation model, not in trained weights. |
| Failure modes | Data drift, concept drift, feature engineering bugs. | Prompt sensitivity, silent model updates by providers, hallucinations, LLM-as-Judge drift, multi-step reasoning errors. |
| Measuring quality | Standard metrics (accuracy, F1, AUC) on well-defined labels. | Quality is subjective and multidimensional (tone, faithfulness, relevance). Requires custom evaluators, often LLM-as-Judge, on sampled production traffic. |
| Determinism | Same input produces same output for a fixed model version. | Same input can produce different outputs (temperature > 0). CI tests must tolerate variation or run multiple times. |

## CI: Building a Safety Net Against Regressions

Continuous integration (CI) in software engineering aims to verify that code changes integrate correctly and do not introduce regressions. This goal applies equally to LLM agents. Traditional machine learning also has CI practices. However, while ML CI might measure overall accuracy against large test sets, LLM CI focuses narrowly on preventing regressions for known failure modes using curated golden datasets ([Table 9-2](#tab_llm_vs_mlops)). CI does not reliably predict overall production accuracy. Its purpose is to ensure stability as the agent evolves.

The foundation of LLM CI is a golden dataset: a hand-curated set of input examples with corresponding reference outputs. We create this dataset through human review and labeling ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), often using collaborative evaluation methods ([Chapter 4](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch04.html#sec_collaborative_evaluation)) to agree on what “correct” looks like.

On each proposed change (a prompt tweak, a model swap, a new tool), we run all golden inputs through the agent and evaluate the outputs with automated evaluators ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)). This is similar to what the Applied LLMs guide calls “assertion-based unit tests”: we take real inputs from production, define at least a few evaluation criteria for each, and check that the agent still meets them.[^1] When using LLM-as-Judge evaluators in CI, pin the exact judge model version (e.g., `gpt-4o-2024-05-13`) to prevent CI results from fluctuating due to unannounced provider updates.

A well-constructed golden dataset should include:

- Examples covering the agent’s core features and capabilities.
- Representative instances of critical failures observed in the past, acting directly as regression tests.
- Challenging edge cases uncovered during error analysis.
- Examples designed to exercise different components or paths within the agent (e.g., specific tool calls, RAG scenarios, different prompt branches).
	Size and scope
	A golden dataset typically includes 100+ examples representing core functionality, previously observed bugs, and known edge cases. It is not a random sample of production data. It is purpose-built to stress-test behaviors we want to preserve.
	Reference-based evaluation
	CI evaluations are reference-based: for each golden input, we check whether the new agent output aligns with the gold reference. As we discover new failure modes (e.g., via monitoring or error analysis), we expand the dataset accordingly.

We illustrate these principles with CI checks from the real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)) in [Table 9-3](#tab_rechat_ci_checks). If any of these checks fail on a corresponding golden example, the CI build should fail, preventing the potentially regressive code change from being merged.[^2]

| Check | Input | Reference | CI evals |
| --- | --- | --- | --- |
| Tone match (LLM Judge) | Agent prompt and client persona | Human-verified, persona-aligned output | LLM judge verifies tone matches expected persona behavior |
| Tool argument schema validation | Query to fetch calendar availability | Tool schema definition | Code-based validator ensures arguments conform to schema |
| Email address existence check | Query instructing an email to a client | Known client email database | Code check confirms recipient address exists |

Maintaining the golden dataset is an ongoing process. As new failure modes or critical edge cases are discovered (often through online monitoring, discussed in the next section), they must be added to the golden set. This ensures the CI safety net expands over time to cover newly understood risks.

## Common Mistakes with CI

We have seen teams commonly make a few mistakes when they start using golden datasets.

The most common is confusing CI pass rate with production quality. A golden dataset is small and curated. Passing CI means the agent still handles the specific cases we have tested. It says nothing about how the agent performs on the thousands of queries it will see in production. Think of CI as a smoke test: if it fails, something is definitely wrong. If it passes, we have not broken anything we know about, but we have not proven anything about general quality either.

Another common mistake is *data leakage*: golden set examples accidentally ending up inside the agent’s prompts as few-shot examples, or inside the LLM judge’s prompts. When the model has already seen the test cases as part of its instructions, it will perform well on those cases regardless of whether it has actually improved. The CI results become meaningless. To avoid this, keep the golden set in a separate file or repository from any prompt content, and audit regularly for overlap.

###### Warning

Data leakage between the golden set and prompts is the most common way teams unknowingly invalidate their CI. If anyone on the team copies a golden example into a few-shot prompt, that example no longer tests generalization. Automate a check that diffs golden inputs against prompt content on every commit.

Teams also ask how large the golden set should be and how often to expand it. A good starting point is 20 to 50 examples covering core features, known failure modes, and edge cases. As the system matures and new failure modes are discovered, the set grows. Mature systems often have 100 to 200 examples. We add examples when we confirm a new failure mode through error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) or online monitoring, not just because more data is available. A bloated test suite is expensive to maintain and slow to debug when tests fail. Every golden example should represent a specific behavior you care about preserving.

## Revisiting Prompts When Models Improve

Foundation models improve over time. When a new model version is released, re-evaluate your prompts, not just running them through CI unchanged.

Many prompts accumulate detailed instructions that were added to work around earlier model limitations. For example, a prompt for a product recommendation summarizer might include the instruction: “The summary should be 4-5 sentences. Start with the product name. End with a recommendation.” If the new model already produces well-structured summaries by default, these instructions may be unnecessary. Removing them can make the prompt cheaper (fewer tokens), faster, and sometimes more accurate, because the model can apply its own judgment rather than rigidly following outdated constraints.

When upgrading to a new model version, we recommend the following process:

1. Run your existing prompts through CI to see what breaks and what still passes.
2. For prompts that pass, try removing the most prescriptive instructions and re-running. If the output quality stays the same or improves, keep the simpler version.
3. For prompts that fail, investigate whether the failure is a genuine regression or just a change in formatting that your evaluators are sensitive to.
4. Re-run error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) on a sample of outputs from the new model. New models can introduce new failure modes as well as fix old ones.

[Voiceflow](https://www.voiceflow.com/pathways/how-much-do-chatgpt-versions-affect-real-world-performance), a company that builds voice and chatbot agents for customers, documented one such migration in late 2023. One of their customers was using an agent to figure out what a user was asking about (for example, “is this a billing question or a shipping question?”) so the company could route the request to the right next step. This kind of agent is usually called an *intent classifier*. When OpenAI released a newer version of GPT-3.5, Voiceflow swapped it in, expecting a drop-in improvement. Instead, accuracy on the customer’s dataset dropped by about 10 percentage points on the exact same prompt. Their team had to go back and rewrite parts of the prompt (changing a phrase from “descriptions and intents” to “descriptions and actions,” adding one worked-out example at the top of the prompt, and leading with a sentence telling the model the task was important) before they could recover the original accuracy. Without a regression test that ran the new model against the customer’s data, they would have shipped the degraded agent to production and found out about the problem only when users complained.

In October 2024, OpenAI quietly swapped the model behind the `gpt-4o` alias. Developers discovered that function calls stopped triggering correctly: the model returned tool responses as plain text instead of structured function calls. Teams that had pinned their model version (e.g., `gpt-4o-2024-05-13`) were unaffected. Teams using the unversioned alias had to scramble to diagnose the issue from customer complaints. The takeaway is to always pin model versions in production and treat a model upgrade as a code change that goes through CI before deployment.

###### Tip

Pin exact model versions (e.g., `gpt-4o-2024-05-13`) in both your agent and your LLM-as-Judge evaluators. Unversioned aliases like `gpt-4o` can change without notice, causing both your agent and your evaluators to shift behavior simultaneously, which makes regressions nearly impossible to diagnose.

## CD and Online Monitoring

We rely on CI to catch regressions on known issues. With CD, we track what happens in production, where users send queries we did not anticipate and the agent encounters situations our golden dataset does not cover.

## Observability

Online evaluation starts with logging. For each production request (or a representative sample), we capture:

- The initial input and relevant metadata (e.g., user/session IDs, flags).
- All intermediate LLM calls: prompts, responses, and intermediate reasoning.
- All tool calls: names, arguments, responses, and errors.
- Retrieved documents in RAG pipelines.
- The final output shown to the user.
- Any user feedback (thumbs up/down, edits, follow-ups).
- Evaluator outputs (if applicable).

These logs let us reconstruct full user interactions. Tools like [LangSmith](https://www.langchain.com/langsmith), [Arize Phoenix](https://phoenix.arize.com/), and [W&B Weave](https://wandb.ai/site/weave/), or integrations with [OpenTelemetry](https://opentelemetry.io/), help manage and explore this data. We recommend reviewing a sample of production traces daily. Developers build a sharper sense of output quality as they see more real data, and we catch emerging patterns earlier when we review daily. The data is organized into *traces*, *spans*, and *sessions* (terms we defined in [“Establishing Terminology”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_establishing_terminology)). A trace is the full record of one user request. A span is one step within that trace (an LLM call, a tool call, a database query). A session groups related traces across a multi-turn conversation.

## Running Automated Evaluators in Production

With logging in place, we run automated evaluators ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)) on sampled production traces. A typical setup uses 5 to 7 evaluators, a mix of code-based and LLM-as-Judge, each tracking a known failure mode.

LLM-as-Judge evaluators are slow and expensive, so we usually evaluate a small sample (1 to 5 percent of traffic) asynchronously after the request completes. For each failure mode, we compute a corrected success rate and a 95% confidence interval using bootstrapping ([“Estimating True Success Rates with Imperfect Judges”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_scaling_judge)). This adjusts for the evaluator’s known TPR and TNR, giving us a grounded estimate of real-world success rates.

For the real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), this might look like:

1. Sample 1% of production traces daily.
2. Run “Hallucinated Tool Usage” and “Location Ambiguity” LLM judges on those traces.
3. Compute the 95% confidence interval for each failure mode’s true success rate.
4. Dashboard the results and alert if any confidence interval crosses a threshold.

## Guardrails

Most evaluators run asynchronously after the fact. *Guardrails* are different. They run *during* execution, before the output reaches the user. Because they sit in the critical path, they need to be fast and have a very low false positive rate. In practice, this rules out LLM-as-Judge for most guardrails: a 2-3 second judge call on every output adds latency users will feel. What does work well is cheap, deterministic checks that run in milliseconds: regex filters, JSON schema validation against the expected output structure, blocklist or allowlist string matches, length/format sanity checks, and lightweight parsers (e.g., `sqlparse` to confirm SQL is syntactically valid, `ast.parse` to confirm Python is parseable).

Concretely, a guardrail is just a function the application calls on every model output before forwarding the response. Here is a minimal Python example wrapping an LLM call for the real estate assistant’s email-drafting feature:

```
import re

# US SSN pattern: 3 digits - 2 digits - 4 digits
SSN_RE = re.compile(r"\b\d{3}-\d{2}-\d{4}\b")
# Simple credit-card-ish pattern: 13–16 digits, optionally separated
CC_RE  = re.compile(r"\b(?:\d[ -]*?){13,16}\b")

def pii_guardrail(text: str) -> tuple[bool, str | None]:
    """Return (is_safe, reason). is_safe=False means block the output."""
    if SSN_RE.search(text):
        return False, "looks_like_ssn"
    if CC_RE.search(text):
        return False, "looks_like_credit_card"
    return True, None

def draft_email(client_request: str) -> str:
    output = llm.complete(prompt_for(client_request))
    is_safe, reason = pii_guardrail(output)
    if not is_safe:
        log_guardrail_trip(reason, output)
        return "I drafted something but it contained sensitive info, " \
               "so I'm asking you to review the source data first."
    return output
```

This pattern — run a fast check on every output, log when it fires, fall back to a safe response when it does — is all a guardrail really is. The check itself can be a regex (as above), a JSON schema validator (e.g., `jsonschema.validate(output, response_schema)` for tool-call arguments), or a parse-and-catch wrapper around a SQL or code parser.

###### Note

A guardrail that fires too often on valid outputs is worse than no guardrail at all. Users experience false positives as broken functionality. Test guardrails against a sample of passing production traces and verify that the false positive rate stays below 1% before deploying.

Guardrails catch things like PII in generated text, syntactically invalid SQL before it runs against the database, or toxic content before it is shown to the user.

When a guardrail triggers, the agent needs a predefined response:

- Reject the output and return a safe fallback message.
- Retry the LLM call. Since LLMs are non-deterministic, a retry often produces a clean output.
- Fallback to a simpler model or logic path.

For the real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)), a guardrail runs a regex check on generated emails before sending. If it detects something that looks like a social security number, it rejects the output. Another guardrail parses generated SQL for syntax errors. If the SQL is invalid, it retries once. If the retry also fails, it asks the user to rephrase.

## Judge Drift

When we first build an LLM-as-Judge evaluator ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)), we validate it against human labels and measure its TPR and TNR. But those numbers do not stay constant. Two things can change under us. First, the model provider can update the LLM that the judge runs on. If we are using an alias like `gpt-4o` instead of a pinned version like `gpt-4o-2024-05-13`, the judge can start producing different scores overnight without any change on our side. Second, the team’s understanding of what “correct” means can shift as they see more production data (the criteria drift we discussed in [Chapter 4](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch04.html#sec_collaborative_evaluation)). The judge was calibrated against labels that reflected the team’s understanding at the time. If the team’s standards have moved, the judge’s scores no longer reflect what the team considers correct.

Either way, the judge’s accuracy degrades without anyone noticing unless we check for it. This is *judge drift*.

We handle this with three practices:

- Pin model versions in both CI and production. Use exact identifiers like `claude-3-opus-20240229`, not aliases like `claude-3-opus`.
- Revalidate regularly. Every few weeks, we sample recent production traces, get fresh human labels, and recompute the judge’s TPR and TNR. If either drops below our threshold, we update the judge’s prompt or few-shot examples and validate the new version before redeploying.
- Re-evaluate after any model change. If we swap the judge’s underlying LLM, we re-run the full validation process.

## The Continuous Improvement Flywheel

CI and CD are not isolated stages. They connect into a loop ([Figure 9-1](#fig-ci-cd-flywheel)). We deploy with monitoring and detect issues in production. Then we diagnose them through error analysis, improve the agent, and update our evaluators. Finally, we verify the fix passes CI and redeploy. Each cycle through this loop makes the system more robust and the evaluation suite more comprehensive.

![ci cd flywheel](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/ci-cd-flywheel.svg)

ci cd flywheel

To make this concrete, here is one full cycle of the flywheel for the real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)).

The team deploys a new version with a neighborhood-targeting feature. They have CI checks for known failure modes (tone mismatch, hallucinated tool usage, missing SQL constraints) and the new version passes all of them.

A week after deployment, the online monitoring dashboard shows a spike in the “Location Ambiguity” failure rate. Product metrics confirm the problem: users in certain neighborhoods have shorter sessions and lower task completion rates.

The team pulls the flagged traces and does error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)). They find that the LLM frequently confuses “West Berkeley” with “Berkeley West” (a non-existent area), producing bad search results. They define a new failure mode: “Directional Location Qualifier Errors.”

Now they update their evaluation artifacts. They add 5 to 10 examples of this failure to the golden dataset, so CI will catch it if it reappears. They build a new code-based evaluator that checks whether generated location strings match known neighborhood names.

They fix the prompt (adding a list of valid neighborhood names to the system message), verify the fix passes CI, and redeploy. The monitoring dashboard shows the failure rate drop. The flywheel has completed one cycle, and the evaluation suite is now more comprehensive than it was before the issue surfaced.

Over time, each cycle through this loop adds new test cases, refines existing evaluators, and catches problems earlier. \[Link to Come\] describes how to build interfaces that make the human review steps in this loop practical and efficient.

## Common Pitfalls

Stale golden datasets

If the golden set stays frozen while production traffic evolves, CI becomes less useful over time. The flywheel example above shows how to fix this: each cycle adds new examples from real failures.

Conflicting metrics

Improving one quality dimension (e.g., conciseness) can degrade another (e.g., factual accuracy). We prioritize our metrics explicitly, especially safety guardrails, and decide how to handle conflicts before they arise.

Disconnected AI and product metrics

A drop in user satisfaction or task completion rates might be an AI quality problem or a UX problem. We investigate both. If the issue is AI quality (e.g., excessive verbosity causing user drop-off), we define a new failure mode and evaluator for it.

Only looking at automated monitoring

LLM-as-Judge evaluators miss subtle failures. Teams that regularly review random production traces (not only flagged ones) catch problems earlier. If user engagement drops but evaluator metrics stay flat, there is likely an undetected issue.

## Putting It Together

In CI, we run golden dataset checks before deployment to catch regressions on known failure modes. In CD, we monitor production traffic to detect new issues we did not anticipate. Together they form a loop in which we deploy, monitor, diagnose, fix, and redeploy.

Automated evaluators handle most of the monitoring, but human review remains necessary for catching subtle or novel failures. The next chapter covers how to build interfaces that make that human review practical and efficient.
