## Chapter 8. Evaluating Tool Use and Complex Agents

So far, we have not thought too carefully about how much autonomy our agents have, or how many tools they use. The techniques in previous chapters (error analysis, automated evaluators, CI/CD) apply whether the agent makes one LLM call or twenty. But as agents become more complex (calling external functions, running multi-step loops, making decisions about what to do next), evaluation gets harder. Errors cascade across steps, and when something goes wrong in the final output, it can be difficult to tell which step caused the problem.

In this chapter, we focus on how to evaluate these systems systematically. We start by defining what tools are and how LLMs use them. We then discuss the spectrum of agency, which determines how much autonomy the system should have. From there, we walk through a four-stage framework for evaluating individual tool calls, a method for debugging multi-step traces, and considerations for handling complex input data like images, long documents, and PDFs.

## What Are Tools and Why Do LLMs Use Them?

On their own, LLMs can only generate text. They cannot look up a property listing in a database, check whether a time slot is available on a calendar, or send an email to a client. To do any of these things, the LLM needs access to external functions. A *tool* is any such function that the LLM can invoke.

We define tools by giving the LLM a list of function names, descriptions of what each function does, and parameter schemas describing what arguments each function expects. When the LLM decides it needs to use a tool, it generates a structured call (typically in JSON format) specifying which tool to invoke and what arguments to pass. The system then executes that call, returns the result to the LLM, and the LLM incorporates the result into its response.

To make this concrete, consider our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)). It has access to several tools: `query_listings` searches a property database with filters, `send_email` drafts and sends messages to clients, and `check_calendar` looks up available showing times. When a user says “Find 3-bedroom houses under $600k and email the top two to my client,” the LLM needs to perform multiple steps. First, it calls `query_listings` with the right filters (bedrooms, price cap, maybe a location). Then it reads the results, selects the top two matches, and calls `send_email` with the right recipient and content. Each of these steps can fail independently.

![tool calling cycle](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/tool-calling-cycle.svg)

tool calling cycle

[Figure 8-1](#fig-tool-calling-cycle) shows this cycle. The LLM receives a user request, decides which tool to call, generates arguments for it, waits for the tool to execute, processes the result, and then either responds to the user or loops back to call another tool. This loop can repeat multiple times before the LLM produces a final answer.

Tools also differ by their potential impact. Read-only tools like `query_listings` can return the wrong results (for example, listings that do not match the user’s price range), but nothing changes in the outside world. The user sees bad data, and we can fix the query. Write tools are different. If `send_email` sends an email with the wrong listing details to a client, or `update_listing` overwrites a price with the wrong number, those actions cannot be undone. When evaluating tool calls, we pay closer attention to write tools for this reason.

###### Warning

If `query_listings` returns the wrong results, the user sees incorrect data but nothing external has changed. If `send_email` sends the wrong message, the recipient has already read it. Evaluate write tools more carefully than read tools.

## The Spectrum of Agency

Before we can evaluate an agentic system, we need to define how much autonomy it should have.

Consider our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)). A user says: “Find 3-bedroom houses under $600k and email the top two to my client.” A *high-agency* version of this assistant would search the listings, pick the top two, draft an email, and send it, all without asking for confirmation. A *low-agency* version would search the listings, show the results to the user, and ask “Should I send these two to your client?” before doing anything irreversible.

Neither behavior is inherently wrong. The right answer depends on what we designed the system to do. If we built a high-agency assistant and it keeps asking for permission, that is a failure. If we built a low-agency assistant and it sends emails without confirmation, that is also a failure.

This is the *spectrum of agency*, and it is one of the first things to define before starting evaluation. Many developers skip this step. The result is that the system behaves in ways that seem wrong, but it is unclear whether the issue is a bug or a gap in the product specification.

Once we have defined the agency level, we can evaluate the agent’s decision-making. During error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), we ask:

- Did the agent make reasonable decisions at each step?
- Did its sequence of actions lead towards the user’s goal?
- Did it show the right level of initiative or caution?
- Did it get stuck in loops or give up prematurely?

One pitfall to watch for is over-relying on final outcomes. End-to-end success matters, but an agent that gets the right answer through an unreliable path will fail on slightly different inputs. We evaluate intermediate steps too.

## Evaluating Tool Calls

Each tool call has its own internal flow. The LLM picks a tool, generates arguments, the tool runs, and the LLM reads the result. If we only check the final output, a failure could be caused by any of these steps and we would not know which one. Decomposing the tool call into four stages ([Figure 8-2](#fig-tool-eval-stages)) lets us pinpoint where things went wrong. The fix is different for each stage: a tool selection error usually means rewriting tool descriptions, while an argument error might mean adding schema validation.

![tool eval stages](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/tool-eval-stages.svg)

## Stage 1: Tool Selection

The first question is whether the LLM picked the right tool. This sounds simple, but it is a frequent source of errors, especially when the available tools have overlapping descriptions or ambiguous names.

Consider our real estate assistant ([“Example: Real Estate Agent Assistant”](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#ex_rechat)). If a user asks “Are there showings available this weekend?” the correct tool is `check_calendar`. But the LLM might instead call `query_listings`, interpreting the question as a search for available properties rather than a calendar lookup. This is a tool selection failure.

Other selection failures include hallucinating a tool that does not exist in the predefined list, or failing to use a tool when one is clearly needed. For example, a user asks “Find houses and email Bob.” If the LLM finds listings but never calls `send_email`, it has failed to complete the requested task.

A common pitfall with tool selection evaluation is focusing solely on whether the tool executes without errors. This neglects the question of whether the LLM chose the *right* tool. If selection errors are frequent, the fix often lies in rewriting tool names and descriptions to make them more distinct, not in changing the LLM’s behavior. We treat tool definitions as a critical, iterable component of the system.

## Stage 2: Argument Generation

Next, we verify the arguments the LLM generated for the selected tool. We check two things: whether the arguments are structurally valid and whether they are semantically correct.

Structural failures include schema or type violations. For example, the LLM might provide `{"price_max": "700k"}` as a string instead of the required integer `700000` for `query_listings`. Another common structural error is missing required arguments, like calling `send_email` without specifying a `recipient_address`.

Arguments can also be structurally valid but have incorrect *values*. The LLM might use the wrong date format (“May 10th”) for a `check_calendar` tool that requires YYYY-MM-DD. Generated arguments should also be checked for security vulnerabilities. Passing unsanitized user input directly into a SQL filter argument risks injection attacks.

We can catch structural issues automatically by defining a *schema* for each tool’s arguments (that is, a description of which fields the tool expects, what type each field is, and which fields are required) and checking every generated call against it. Here is a short example using Pydantic, a Python validation library:

```
from pydantic import BaseModel, Field
from datetime import date

class CheckCalendarArgs(BaseModel):
    date: date = Field(
        description="Date to check, in YYYY-MM-DD format"
    )
    agent_id: str = Field(
        description="ID of the real estate agent"
    )

# If the LLM generates {"date": "next Saturday", "agent_id": "a123"},
# this will raise a validation error because "next Saturday"
# is not a valid date.
args = CheckCalendarArgs(**llm_generated_args)
```

If the LLM produces `{"date": "next Saturday"}`, Pydantic raises an error immediately, before the tool ever runs. This catches type mismatches, missing fields, and format violations. Catching incorrect *values* (for example, a date that is valid but in the past) may require additional checks beyond the schema, such as rule-based validators or lookups against reference data.

## Stage 3: Execution

Even if the LLM selected the right tool and generated valid arguments, the tool call itself can fail.

Consider a call like `query_listings(property_id="98765")`. It might pass schema checks if the ID format is correct. However, if property 98765 does not exist in the database, the query returns an empty result. This is a common silent failure.

The tool can also produce runtime errors. A call to an external service like `search_web("latest mortgage rates")` could fail due to a temporary network issue or an API timeout. When architecting LLM agents, it is helpful to capture and log any error messages or tracebacks from tool failures, so that error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)) is easier.

## Stage 4: Output Handling

After the tool executes successfully and returns its result, we assess whether the LLM correctly interpreted that result. Failures here are specific to the LLM’s processing, assuming the tool itself worked correctly.

One failure mode is the LLM *misinterpreting* specific data points. For example, `query_listings` returns details for a property including `"sqft": 1500`, but the LLM states that the property is “over 2000 sq ft.”

Another common failure involves the LLM *ignoring important details*. For instance, `query_listings` might return two properties, one with a clear agent note “structural issues reported.” If the LLM omits this when presenting the options to the user, that is a potentially serious oversight. These omissions are domain-specific and are typically only uncovered during careful error analysis.

A different failure mode is failing to integrate the tool’s output logically into the conversation. For example, `check_calendar` returns available slots `["Saturday 2pm", "Sunday 4pm"]`, but the LLM asks the user “When are you free?” instead of proposing the specific times the tool discovered.

Detecting these interpretation failures automatically is challenging. It often requires human review or carefully designed LLM-as-judge evaluations ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)) focusing on semantic consistency between the tool output and the LLM’s response.

## Why Evaluate Each Stage Separately

Evaluating each stage separately is crucial because failures cascade. Poor argument generation might cause execution errors or lead to misinterpretation, even if the LLM handles correct output well. Pinpointing the exact stage of failure (selection, arguments, execution, or output handling) directly informs where interventions like prompt refinement or schema adjustments are needed.

Uber’s QueryGPT is an example of this approach.[^1] QueryGPT is an internal agent used by Uber employees to ask questions about company data in plain English, like “how many trips did we do in San Francisco last week?” The agent translates the question into a SQL query, runs it against Uber’s databases, and returns the answer.

The team built it as a chain of specialized sub-agents. An *intent agent* looks at the question and decides which part of the business it relates to (rides, food delivery, advertising, and so on), so that later steps know which databases to search. A *table agent* picks the specific tables in those databases that are likely to contain the answer. A *column-prune agent* removes irrelevant columns, keeping the context passed to the LLM manageable. Finally, the system generates the SQL query.

To evaluate the whole system, the team does not just check whether the final SQL query is correct. They measure each sub-agent separately:

Intent accuracy

Did the intent agent pick the right part of the business?

Table overlap

Did the table agent pick the right tables?

Execution success

Did the generated SQL run without errors?

Query similarity

How close is the generated SQL to a hand-written reference query? (They use an LLM judge to compare the two.)

The first three are stage-level checks. The fourth is an end-to-end check. When an overall metric drops, this multi-signal approach lets the team see which stage regressed.

Two more things about tool calling. First, the quality of tool descriptions has a large effect on how well the agent uses them. The names, descriptions, and parameter specifications we provide to the LLM influence which tool it selects and how it fills in the arguments. If tool names are ambiguous or descriptions are vague, the LLM will struggle at Stage 1 regardless of how good the model is. We iterate on tool descriptions the same way we iterate on system prompts.

###### Note

Tool descriptions are prompts too. When the LLM selects the wrong tool or generates bad arguments, the fix is often to rewrite the tool’s name, description, or parameter schema, not to change the system prompt or the model.

Second, standardized protocols like the Model Context Protocol (MCP) are increasingly used to structure how LLMs interact with tools. MCP defines a consistent format for tool calls, argument passing, and response handling. From an evaluation standpoint, these protocols do not change the fundamental questions we ask. We still need to check tool selection, argument quality, execution success, and output handling. But they do make logging and traceability significantly easier by providing structured, parsable records of every tool interaction.

## Debugging Multi-Step Traces

Agentic systems generate multi-step traces. A single user request might produce a sequence of five or ten tool calls, each building on the results of the previous ones. When something goes wrong in the final output, we need to find where the error originated. This is harder than it sounds, because an error in an early step can easily cascade into seemingly unrelated failures later on.

## Traceability

The core principle enabling effective debugging is *traceability*. When we record a trace, we capture as much information as possible at each stage of the agent’s execution. This includes the inputs and outputs at each step, along with intermediate reasoning or “thoughts” generated by the LLM, any tool calls together with their arguments and responses, and the decisions reached.[^2]

Without comprehensive logging, pinpointing the root cause of failures becomes exceptionally difficult. If we do not know what the LLM was “thinking” between tool calls, we cannot tell whether the problem was a bad tool result or a bad interpretation of a good result. Effective debugging hinges on our ability to reconstruct and analyze the agent’s behavior at every step.

###### Tip

Log every intermediate step from the start, even before you have evaluators to consume it. Inputs, outputs, tool arguments, tool responses, and the LLM’s internal reasoning are all cheap to store and painful to reconstruct after the fact. When a production failure occurs, the trace log is the first thing you will consult.

We also evaluate individual agent components in isolation. For example, checking the quality of PDF text extraction before LLM reasoning, or testing a specific tool’s reliability before integrating it into a complex agent, helps us attribute errors correctly. Both component-level and end-to-end evaluations are necessary for a complete understanding of agent performance.

## From Traces to Systemic Patterns

Manual trace inspection explains individual failures well. However, it does not scale. When we have hundreds or thousands of traces, we need a systematic method to find the most common failure points across many runs.

The method works as follows. First, we define discrete *states* representing significant stages in the agent’s execution paths. Typically, each distinct tool call corresponds to one or more states. For example, generating arguments for `query_listings` might be state `GenArgs`, executing the query might be state `ExecTool`, and processing the result might be state `HandleOut`. We can also define states for internal LLM reasoning steps, such as `UpdatePlan` or `DecideNextAction`.

Next, we collect a dataset of execution traces, each labeled with its outcome (success or failure). For the traces marked as failures, we identify the *first state* in the sequence where something demonstrably went wrong. This identification can use automated component-level evaluators (like schema validators or faithfulness checkers) or human annotation guided by predefined failure criteria for each state.

One important principle is to focus on the *first* failure. Errors cascade. A mistake in an early state can lead to seemingly unrelated failures later on. By attributing the failure to the first state where criteria were violated, we avoid incorrectly blaming downstream components that might have acted reasonably given faulty inputs.

## The Transition Failure Heatmap

Instead of simply counting where failures originate, we gain more insight by analyzing the *transitions* between states that lead to failures. We build a *transition failure heatmap* where rows represent the “From State” (the last successfully completed state) and columns represent the “In State” (the state during which the first failure occurred). Each cell counts the number of traces where a failure happened in the column’s state immediately after successful completion of the row’s state.

![transition failure heatmap](https://learning.oreilly.com/api/v2/epubs/urn:orm:book:9798341660717/files/assets/transition-failure-heatmap.svg)

transition failure heatmap

[Figure 8-3](#fig-transition-failure-heatmap) shows an example for a simplified version of our real estate assistant. We define four agent states: `ParseReq` (parse the user request), `GenArgs` (generate tool arguments), `ExecTool` (execute the tool call), and `HandleOut` (handle the tool output). The heatmap immediately surfaces hotspots. The most frequent transition leading to a first failure (12 instances) occurs when entering `ExecTool` immediately after completing `GenArgs`. This tells us that the LLM is generating arguments that pass schema validation but cause the tool to fail at execution time. Perhaps the LLM is referencing property IDs that do not exist, or constructing SQL queries with syntax that the database does not support.

To identify the overall most frequently failing state, we sum the failure counts in each column. In this example, `ExecTool` has the highest column total (12), followed by `HandleOut` (7) and `GenArgs` (8).

## Investigating Hotspots

When investigating a specific hotspot like the `GenArgs` to `ExecTool` transition, we start by isolating those 12 specific traces. We analyze what went wrong *during* the `ExecTool` state, critically examining the context provided by the preceding `GenArgs` state when performing error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)).

Why track the “From State” and not just count column totals? Column sums identify the overall most error-prone state, but this alone can be misleading. A state like `ExecTool` might fail frequently after LLM-generated arguments but succeed reliably after simpler inputs (for example, when the user specifies a query directly). Tracking the “From State” allows a finer-grained analysis that pinpoints the specific *transitions* or *contexts* leading to failure.

Note that identifying the transition pinpoints *where* to begin investigating, but it does not automatically imply that the preceding state is the sole cause. The root issue might lie in the preceding state, or it might lie within the failing state itself. For example, our database might use a SQL dialect that we did not mention in the agent’s prompt.

## Evolving the Heatmap Over Time

As we iteratively debug the agent, we expect the failure heatmap to evolve. Fixes to prompts, tool schemas, validation logic, or agent reasoning should reduce the counts in identified hotspots. Over time, the heatmap should become sparser and show lower overall intensity. Ideally, it converges toward a stable pattern reflecting the system’s improved robustness, with only residual errors or inherently difficult transitions remaining.

We can also create a similar heatmap tracking *all* state transitions (counting successes) to map the agent’s common operational patterns. This helps us understand which pathways are frequently used and which are rarely exercised, informing where to focus testing efforts.

## Handling Complex Input Data

Agentic systems often process complex inputs like images, long documents, and PDFs. Each of these introduces modality-specific failure modes that we need to account for during evaluation. The key principle for all of them is to separate input processing errors from LLM reasoning errors.

## Images

*Vision-Language Models* (VLMs) are LLMs that can also take images as input, sometimes alongside text prompts, and can generate descriptions, answer questions about what they see, or even edit images. Most recent frontier models (GPT-4o, Claude 3.5 Sonnet, Gemini 2.0) are VLMs. They are generally effective at describing visual properties of individual objects, such as color, shape, and material.

Common issues to check for in error analysis include errors in spatial reasoning (misjudging positions like left/right or above/below), counting objects incorrectly, struggling to recognize text within the image, and hallucinating objects or details not actually present.

The core evaluation techniques from earlier chapters apply directly. We define clear evaluation criteria and detailed rubrics ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)). The key implementation difference is the need for visual grounding: human evaluators must reference the image, and any automated judge must itself be a capable VLM.

Evaluating image *generation* (text-to-image) raises different issues. Unlike text models that generate token-by-token, many image generators start with noise and refine pixels across the entire image in parallel. Because they do not build the image object-by-object, they struggle to enforce global constraints like exact counts or distinct identities for multiple objects. For example, asking for “an image of 3 presidents” might produce three copies of the same person or figures that look like strange combinations. A more structured prompt like “Obama, Trump, and Biden standing left to right” gives the model better guidance. Evaluating these compositional aspects often requires careful human review or VLMs to serve as judges of correctness.

## Long Documents

LLMs encounter difficulties with very long text inputs. While context window limits are the obvious constraint, many studies have found that task accuracy degrades as context grows, even when the text fits within the window.

How we evaluate long-document agents depends on the task. We can distinguish two common workload types.

*Constant output tasks* (sometimes called “needle-in-a-haystack”) are those where the LLM needs to find a small amount of information from within a long document. The scope of information needed does not grow because the document is longer. These tasks might involve finding a few specific facts, identifying a concept, or performing reasoning based on localized information. Error analysis should focus on whether performance drops significantly when the needed information appears in the middle of the context window rather than near the beginning or end.

*Variable-size output tasks* produce outputs that grow with the document length. Examples include extracting all names in a transcript, summarizing every section of a report, or identifying each angry comment in a script. Since the LLM may not be able to process the full document at once, we break it into smaller chunks, process each chunk independently, and then aggregate the results.

The challenge is to find the largest chunk size that still lets the model perform the task reliably. Simple tasks like “extract all names mentioned in this chunk” can work well with longer chunks (2k to 4k tokens). More complex tasks that involve reasoning, transformation, or tracking many internal elements often fail if the chunk is too large. A good rule of thumb is to keep each chunk focused on roughly 3 to 5 ideas or spans of content that the LLM needs to reason about.

Evaluating long-document agents follows the same basic steps we have used throughout this book: start with error analysis ([Chapter 3](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch03.html#sec_error_analysis)), define metrics, and scale evaluation using methods like LLM-as-judge ([Chapter 5](https://learning.oreilly.com/library/view/evals-for-ai/9798341660717/ch05.html#sec_implementing_evaluators)). For long documents, LLM-as-judge needs special handling. We usually cannot feed the full document into the judge due to context limits and accuracy degradation. Instead, we give the judge just the relevant portion, such as the paragraph a summary sentence came from, or the snippet where an entity was supposedly extracted. Another approach is chunk-level evaluation, where we ask the judge to evaluate output chunk-by-chunk and then aggregate the per-chunk judgments.

## PDF Documents

PDF agents begin by extracting text and structure from the file to prepare input for the LLM. This extraction step is often the biggest source of errors. Common problems include incorrect text (especially from OCR on scanned documents), broken tables, and text that is read in the wrong order due to complex layouts.

Extraction quality depends heavily on the type of PDF. Digitally generated PDFs usually extract cleanly, but scanned documents often produce noisy, error-prone text. Even when extraction succeeds, how we format the result for the LLM matters. Presenting a table row-by-row can yield different results than formatting it column-by-column.

To evaluate these agents, we separate extraction errors from LLM reasoning failures. That means inspecting the actual extracted content the LLM saw, not just the original PDF. Otherwise, we risk blaming the model for mistakes caused by bad input. This is another case where component-level evaluation is essential for correctly attributing errors and knowing where to direct our improvement efforts.

## Putting It Together

Evaluating agentic systems requires thinking about both the individual steps and the overall behavior of the agent. We start by deciding how much agency the system is supposed to have, since that decides what we are even calling a failure. For tool calls, we check tool selection, argument generation, execution, and finally output handling. For multi-step traces, we use state-based analysis and transition failure heatmaps to identify the most common failure points across many runs. When agents process complex inputs like images, long documents, or PDFs, we add modality-specific checks and separate input processing errors from reasoning failures.
